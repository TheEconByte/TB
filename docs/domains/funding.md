# 자금 카탈로그·후보 도메인

이 문서는 카탈로그 검증·적재, 동기화와 조건 추출, 맞춰 보기, API 정책을 다룬다. 카탈로그 편집 절차, 필드 기록 규칙, 현재 확인 범위는 [app/catalog/funding/README.md](../../app/catalog/funding/README.md)에 있다.

## 코드 위치

- `app/src/features/funding`: 판정 함수는 React·DB·외부 API에 의존하지 않는다.
  - 카탈로그 Zod 스키마(`schema.ts`), 규칙 검사와 상환 계산 대상 여부(`validation.ts`)
  - 릴리스·상품 버전 적재, 활성 카탈로그 읽기(`read.ts`)
  - 출처별 수집 결과를 사람이 관리하는 카탈로그와 합쳐 적재하는 동기화(`sync.ts`), 출처별 수집기(`sources/`)
  - 공고 파일(PDF·HWP·HWPX)을 텍스트로 바꾸는 `notice-text.ts`. funding:sync의 본문 수집에서만 쓴다(아래 공고 본문과 AI 추출 결과). HWP·HWPX 표는 칸 안의 문단마다 한 줄이고(빈 칸은 빈 줄) 행·칸 구분 표시가 없다. 각주·미주·머리말·꼬리말은 빠진다. PDF 표는 행마다 한 줄이고 칸 사이가 공백이다.
  - [ADR 0009](../decisions/0009-funding-ai-condition-extraction.md) §4의 맞춰 보기: 추출 결과의 이름·저장 모양(`condition-fields.ts`), 판정(`matching.ts`), 활성 카탈로그와 추출 결과 읽기(`match-list.ts`), 사용자 입력 스키마와 저장된 조건 읽기(`match-profile.ts`)
  - 맞춰 보기 화면: 페이지 단위 화면(`FundingMatcher.tsx`), 두 화면이 함께 쓰는 입력란(`FundingProfileFields.tsx`, 상태와 본문 변환은 `profile-form.ts`)과 결과 표시(`FundingMatchesPanel.tsx`), 판정 코드를 문장으로 바꾸는 `match-text.ts`
- `app/catalog/funding`: 운영자가 공식 공고를 정리한 JSON 카탈로그와 갱신 절차 문서.

## 카탈로그

- 실행: `npm --prefix app run funding:validate`, `npm --prefix app run funding:load [-- --catalog <경로>]`. 기본 카탈로그는 `app/catalog/funding/catalog.json`이다.
- 원문 확인과 카탈로그 편집은 운영자가 수행한다.
- Zod 스키마가 productKey·version 형식, 필수 필드, 날짜 형식, 금액의 원 단위 정수 문자열, supportType·사업단계·접수 상태·상환방식 열거, 공식 기관 HTTPS 호스트, checksum 형식을 검사한다.
- 상환 계산 대상 여부(`validation.ts`의 `repaymentCalculationReasons`). 규칙 검사의 계산 사유 확인과 적재기가 `funding_product_versions.repaymentCalculationSupported`에 남기는 값이 이 판단 하나를 쓴다. 기록 규칙은 카탈로그 README의 "확정 조건과 상환 계산"에 있다.
  - 구조화된 확정 조건 필드(`interestRatePercent`·`repaymentTermMonths`·`repaymentGraceMonths`)만 읽는다. 조건 문장(`interestCondition`·`repaymentCondition`)은 숫자로 해석하지 않는다.
  - 대출(LOAN)만 대상이다. 지원금·보증·공간·프로그램 지원과 유형 미확인 공고는 대출 원금이나 상환 일정으로 바꾸지 않는다.
  - 공개 한도, 확정 금리(`interestRateConfirmed`와 `interestRatePercent`), 상환기간·거치, 계산 엔진이 지원하는 상환방식(원리금균등·원금균등)이 모두 있어야 대상이다. 거치가 상환기간 이상인 상품은 규칙 검사가 거부한다.
  - 대상이어도 상품 조건을 계획에 옮기지 않는다(아래 저장된 대출 가정).
- 규칙 검사 항목:
  - productKey+version 중복
  - 접수기간과 관측 접수 상태의 모순(종료된 공고를 OPEN으로 기록 등)
  - 지원 유형과 금리·상환 조건의 모순, 확정 조건의 내부 모순
  - 원문 미확보 상태의 checksum
  - 상환 계산 사유 누락·불필요, 조건별 공식 근거 누락
- 다음은 오류가 아니라 주의로 기록한다: 공식 원문이 아닌 요약 근거, 신청기간 종료일 전의 CLOSED 기록(조기 마감이면 근거를 추가한다).
- `funding:validate`는 맞춰 보기 갈래별 상품 수와 마감 수를 사용자 입력·AI 추출 결과 없이 본 기준으로 출력한다.
- 검증을 우회하는 명령행 옵션은 없다. 조건이 불명확한 상품을 강제로 활성화하는 경로를 만들지 않는다.
- 스키마 `funding-catalog-v1.1.0`은 v1.0.0에 다음을 더했다. v1.0.0으로 적재된 릴리스도 읽으며, 그때 자동화 설정은 차단 목록·동기화 결과가 빈 기본값이다.
  - 상품의 `sourceRef`(출처와 공고 식별자). funding:sync가 모은 상품에 붙고, 사람이 기록한 상품도 같은 공고를 가리키면 적는다.
  - 카탈로그의 `automation`: 정책자금 자동 승격(`policyLoanPromotion`)·상환 계산 자동 승격(`repaymentPromotion`) 스위치, 차단 목록(`blockedSources`), 출처별 동기화 결과(`sourceSyncs`). 스위치는 v1.5.0에서 없앴다.
- 스키마 `funding-catalog-v1.2.0`은 v1.1.0에 원문이 알려 주지 않는 값을 추측 없이 기록하는 방법을 더했다. 이전 버전의 릴리스도 읽는다.
  - 지원 유형 `UNKNOWN`(DB enum `FundingSupportType`에도 있다). 상환방식은 `UNKNOWN`이어야 하고 확정 금리·상환기간·거치를 기록할 수 없다. 금융 조건 근거를 요구하지 않는다.
  - `eligibleBusinessStages`의 빈 배열은 사업 단계 미확인이다. 이때 사업 단계 근거를 요구하지 않는다.
- 스키마 `funding-catalog-v1.3.0`은 v1.2.0에 상품의 `noticeTextChecksum`(funding:sync가 쓴 공고 본문의 checksum, [ADR 0009](../decisions/0009-funding-ai-condition-extraction.md))을 더했다. 이전 버전의 릴리스도 읽는다.
- 스키마 `funding-catalog-v1.4.0`은 v1.3.0에 상품의 선택 필드 두 개를 더했다. 이전 버전의 릴리스도 읽으며, 그때 두 필드는 없다.
  - `sourceCategory`: 출처가 준 지원분야 원문 값(기업마당 `pldirSportRealmLclasCodeNm`). 정책자금·지원사업 갈래를 정한다(ADR 0009 §1).
  - `limitText`: 출처가 준 한도 문장(소진공 대출한도 칸). 정책자금 카드에 참고로만 보여 주고 계산에 쓰지 않는다.
- 스키마 `funding-catalog-v1.5.0`은 [ADR 0009](../decisions/0009-funding-ai-condition-extraction.md) §7에 따라 ADR 0006의 검수자·검수 기한·스위치를 없앴다.
  - 없앤 것: 상품의 `reviewer`·`reviewedAt`·`nextReviewAt`, 카탈로그의 `reviewer`, `automation`의 두 스위치. 규칙 검사의 검수일·다음 검토일·검수 기한 경과·검수자 미지정 항목도 없앴다.
  - 더한 것: 상품의 `origin`. `SYNC`는 funding:sync가 모은 상품(자동 상품), `OPERATOR`는 운영자가 `catalog.json`에 기록한 상품(사람 상품)이다. 기본값이 없어 빠지면 스키마 오류다. 맞춰 보기의 갈래·운영자 확인 값·출처 최신성·운영자 숨김이 이 값으로 갈린다.
  - 이전 버전의 릴리스도 읽는다. 그 상품은 검수자가 `AUTO:`로 시작하면 `SYNC`, 아니면 `OPERATOR`로 읽는다. 둘 다 없으면 짐작하지 않고 읽기를 실패시킨다. 저장된 스위치는 읽지 않는다.
- 규칙 검사는 다음을 오류로 본다: 출처 식별자 없는 `SYNC` 상품, 같은 공고를 가리키는 상품 두 개, 같은 출처의 동기화 결과 두 개.
- 웹 페이지 근거(`OFFICIAL_WEB_PAGE`)의 checksum은 사람이 기록한 상품에서는 오류다(내려받은 파일이 없다). 자동 상품에서는 funding:sync가 실제로 받은 응답이므로 그 페이지의 checksum을 남길 수 있다.

### 릴리스와 상품 버전

- 릴리스에는 출처 목록(`sourceDocuments`), 이 카탈로그가 담은 상품 버전 목록(`productVersions`), 기준일(`basisDate`), `schemaVersion`, 카탈로그 checksum, 검증 요약을 함께 보존한다.
  - v1.4.0까지는 릴리스의 검수자·검수일과 상품 버전의 검수일·다음 검토일 열도 있었다. migration `20261104010000_funding_remove_review_fields`로 지웠다. 상품 버전의 두 날짜는 `productJson`에 남는다.
- 카탈로그 checksum은 파일 바이트의 SHA-256이다. `funding_catalog_releases.catalogChecksum`이 UNIQUE라서 같은 내용을 다시 적재해도 릴리스가 늘지 않고 `ALREADY_ACTIVE`로 끝난다. 같은 catalogKey+catalogVersion에 다른 내용이 오면 거부한다.
- 상품 버전(`funding_product_versions`)은 `productKey + version`이 UNIQUE이며 불변이다.
  - 이미 적재된 버전과 내용이 다르면 `PRODUCT_VERSION_IMMUTABLE`로 실패하고 기존 행을 덮어쓰지 않는다. 새 내용은 version을 올려 추가한다.
  - 릴리스와 상품 버전은 `funding_catalog_products` 연결 테이블로 묶어, 같은 불변 버전을 여러 릴리스가 재사용할 수 있다.
- 적재는 PENDING으로 시작해 적재 후 검증까지 통과한 뒤 한 트랜잭션으로 ACTIVE가 된다. 활성화는 상태 전환만 하며 과거 릴리스와 상품 버전을 지우지 않는다.
- 실패하면 이번 적재가 만든 상품 버전만 삭제하고, 이전에 이미 저장된 상품 버전은 그대로 둔다. 릴리스는 `FAILED`와 실패 사유(`오류 코드 + 메시지`)로 남는다.
- 릴리스의 `automation`(JSONB)에 자동화 설정과 출처별 동기화 결과를 저장한다. v1.0.0 릴리스는 NULL이다.

### 동기화

[ADR 0006](../decisions/0006-funding-discovery-automation.md)의 동기화다. 실행 명령은 [DEVELOPMENT.md](../DEVELOPMENT.md#로컬-데이터-준비)에 있다.

- 흐름: 출처별 수집기(`FundingSourceAdapter`)로 공고를 받아 상품을 만들고, 사람이 관리하는 `catalog.json`의 상품과 합친 뒤, 위 적재기와 같은 검사로 `PENDING → ACTIVE` 적재한다.
- 합친 카탈로그:
  - catalogKey와 차단 목록은 `catalog.json`을 따른다. 기준일은 동기화한 날(한국 시간)이다.
  - catalogVersion은 `동기화한 날.번호`다. 같은 날 적재된 릴리스와 `catalog.json`의 버전을 피해 번호를 올린다.
  - 적재한 카탈로그 파일은 `data/funding-sync/`(Git 제외)에 남는다.
- 상품 버전: 날짜와 근거 checksum을 뺀 내용이 이미 적재된 버전과 같으면 그 버전을 재사용한다. 다르면 가장 높은 버전의 PATCH를 올린다.
  - v1.4.0까지 저장된 예전 모양 버전(검수자가 있고 `origin`이 없음)은 다시 쓰지 않는다. 읽을 때 출처 구분을 채워 저장된 원문과 달라지므로, 다시 쓰면 불변 검사(`PRODUCT_VERSION_IMMUTABLE`)에 걸린다. 그래서 v1.5.0 뒤 첫 동기화에서 자동 상품 전부가 한 번 새 PATCH 버전이 된다. 공고 본문 checksum은 그대로라 AI를 다시 부르지 않는다.
- 출처가 실패하면 그 출처의 상품은 직전 ACTIVE 릴리스의 것을 그대로 두고, 마지막 성공일(`lastSucceededOn`)과 공고 수도 그대로 둔다. 가져온 상품의 버전은 위 규칙으로 다시 정한다(지금 모양이면 같은 버전, 예전 모양이면 새 버전). 다음은 실패다.
  - 수집기 오류(장애·인증 오류·차단 등)
  - 빈 응답. "공고 없음"으로 해석하지 않는다
  - 받은 공고 수가 직전 성공의 절반 미만
  - 수집한 상품이 카탈로그 규칙 검사를 통과하지 못함, 다른 출처의 상품, 같은 공고 두 번, 사람이 기록한 상품 키와 겹침
- 사람이 기록한 상품이 같은 공고(`sourceRef`)를 가리키면 자동 상품을 빼고 사람 기록을 쓴다.
- `catalog.json`에 `origin`이 `SYNC`인 상품이 있으면 거부한다. 자동 상품은 funding:sync만 만든다.
- 수집 출처와 허용 확인 기록. 출처는 robots.txt와 약관을 확인한 뒤에만 수집기를 등록한다(ADR 0006 3절).

#### 소진공 정책자금 수집

정책자금 갈래의 자동 수집 출처다(ADR 0006 1·3절). 접수 상태를 홈 화면 접수 표시로 정하고 상품을 자금 단위로 식별하는 것은 [ADR 0007](../decisions/0007-semas-ols-status-and-fund-identity.md)이 정한다. 첨부(PDF)는 읽지 않는다. 자금 행·공통 지원자격·공지 본문은 아래 공고 본문으로 모으고 조건은 AI가 읽는다(ADR 0009).

- 읽는 곳(모두 로그인 없는 공개 페이지):
  - 정책자금 한눈에 보기(`/ols/man/SMAN018M/page.do`): 직접대출·대리대출 표의 자금명·신청요건·대출기간·대출한도·대출금리, 공통 지원자격, 분기 기준금리.
  - 홈 화면(`/ols/man/SMAN010M/page.do`)의 "정책자금 신청하기": 자금별 접수 상태 표시("접수중")와 접수기간. ADR 0006 4절 1번의 "출처의 접수 상태 표시"로 쓴다.
  - 공지사항 목록 JSON(`/ols/man/SMAN051M/search.do`, POST): 자금별 최신 접수 안내 공지를 찾는 데만 쓴다. 조건 값은 읽지 않는다. 최근 30쪽까지 읽는다.
  - 공지 상세(`/ols/man/SMAN052M/page.do?bltwtrSeq=…&bbsTypeCd=…`): 접수기간·신청대상 문장과 '제외'가 들어간 줄.
- 요청 규칙:
  - 수집 전에 `/robots.txt`를 요청한다. 확인 때처럼 404가 아니면(새로 생기면) 멈춘다. 사람이 허용 여부를 확인해 위 표에 기록한 뒤 수집기를 고친다.
  - 요청 사이 1초 이상 쉰다(기본 1.5초). User-Agent는 `TrendBench-funding-sync/1.0 (+FUNDING_SYNC_CONTACT)`다. 연락처가 없으면 요청하지 않고 실패한다.
  - 403·429·자동 입력 방지 화면을 만나면 다시 시도하지 않고 멈춘다. 서버 오류·연결 오류만 두 번까지 다시 시도한다.
- 실패(필수 항목 없음): 자금 표·표 머리글·직접/대리 구분·공통 지원자격의 소상공인 문장·"정책자금 신청하기" 영역을 찾지 못함, 공지 목록이 JSON이 아니거나 비었거나 전체 건수보다 적음, 공지 상세의 제목·본문이 없거나 제목이 목록과 맞지 않음. 받은 공고 수(`fetchedCount`)는 표의 자금 행 수다.
- 상품 하나 = 표의 자금 한 행이다. 공지는 분기·월마다 새로 올라오므로 공지 번호 대신 대출구분과 자금명으로 식별한다.
  - 출처 식별자는 `SEMAS_OLS:대출구분:자금명`(공백과 앞머리 '소상공인'을 뺀 이름, 예: `대리대출:일반경영안정자금`)이다. 차단 목록과 사람 기록 우선도 이 식별자로 맞춘다.
  - 상품 키는 `semas-ols-direct-…`·`semas-ols-agency-…`와 식별자 SHA-256 앞 10자리다.
  - 같은 자금이 표에 두 번 나오면 뒤 행을 빼고 센다. 표에 없는 홈 화면 대출 카드는 명령 출력에 나열한다.
- 공지 고르기: 같은 대출구분의 '대출정보' 공지 중 제목에서 자금명 바로 뒤에 (직접대출)·(대리대출)·(일반)과 '접수 안내'·'신청안내'만 오는 공지 가운데 번호가 가장 큰 것. '금리인하제도 신청안내'처럼 다른 제도의 안내와 '(홈플러스 피해 소상공인)'처럼 대상을 좁힌 세부 공고는 고르지 않는다.
- 상품으로 옮기는 값:
  - 지원 유형 LOAN, 사업 단계 미확인(빈 배열)·지역 UNKNOWN, 용도·업종 UNKNOWN(신청 전 확인), 기관 소상공인시장진흥공단. 사업 단계·지역은 공통 지원자격에서 추측해 적지 않고 근거도 남기지 않는다. 그 조건은 본문에서 AI가 읽는다(ADR 0009 §7).
  - 금리는 `interestCondition`에 표의 금리와 기준금리 문장을 그대로 적고 확정 금리로 기록하지 않는다. '기준금리+가산'은 변동금리이고, '고정금리(2.0%P)'는 연 금리인지 가산폭인지 모호하다. 표에 상환방식이 없어 상환방식 UNKNOWN, 상환기간·거치 null이다. 따라서 상환 계산 대상이 아니다(ADR 0006 5절).
  - 공개 한도는 대출한도 칸이 금액 하나일 때만 원 단위로 옮긴다(예: '7천만원'). 유형·용도별 금액이 여럿이면 null이다.
  - 대출한도 칸의 문장은 금액이 여럿이어도 그대로 `limitText`에 옮긴다.
  - 공식 링크는 고른 공지 상세, 없으면 정책자금 한눈에 보기다.
  - 근거는 모두 `OFFICIAL_WEB_PAGE`이며, 근거마다 그 근거를 읽은 페이지 응답(한눈에 보기·홈 화면·공지 상세)의 SHA-256을 checksum으로 남긴다(ADR 0006 2절). 공지 목록까지 포함해 읽은 페이지 전체의 checksum은 출처별 동기화 결과의 `responseChecksum`에 남는다. 날마다 바뀌는 checksum은 상품 버전 비교에서 빠지므로 버전이 늘지 않는다.
  - 신청대상 문장, 세부 유형만 접수 중인 카드, 상태 판정의 모순, 제외 신호는 신청 전 확인 항목에 적는다.
- 접수 상태:
  - OPEN: 홈 화면에 그 자금(세부 유형이 아니라 자금 이름 그대로)이 "접수중"으로 표시되고, 시작일이 판정 기준일 이전이며, 종료일이 지나지 않았고, 공지의 접수 시작일·종료일과 어긋나지 않을 때만이다. 날짜 없는 '상시접수'도 "접수중" 표시가 있으면 OPEN이다.
  - CLOSED: 홈 화면 표시가 '마감'·'종료'일 때.
  - 그 밖은 UNKNOWN이다: 홈 화면에 표시가 없음, 세부 유형 카드만 있음, 알 수 없는 표시, 날짜 모순. 신청기간은 공지 접수기간으로 남기므로, 종료일이 지난 공지는 판정에서 접수 종료가 된다.
  - 홈 화면 종료일이 없고(자금소진시까지) 공지에 종료일이 있으면 공지 종료일을 쓴다.
- 제외 신호: 공통 제외업종 또는 공지의 '제외' 줄에 음식점·외식·카페 등이 보이면 OPEN으로 기록하지 않고 확인 항목에 남긴다(ADR 0006 4절 3번·6절). 유흥주점 같은 표현은 신호로 보지 않는다.
- 맞춰 보기: 정책자금 갈래다. 접수 상태가 OPEN이고 출처가 최신일 때만 맞아 보임이 될 수 있다(아래 맞춰 보기).

#### 기업마당 공고 탐색

기업마당 목록의 항목으로는 사업 단계·지원 유형을 알 수 없다. 조건은 공고 본문에서 AI가 읽는다(ADR 0009 §2·§3, 아래 공고 본문과 조건 추출).

- 요청: `BIZINFO_API_KEY`로 하루 한 번, 요청 한 번(`searchCnt` 5000)에 현재 공고 전체를 JSON으로 받는다. 오류 문장과 명령 출력에서 키를 가린다.
- 실패: 키 없음, 403·429(다시 시도하지 않고 멈춘다), 서버 오류·연결 오류가 세 번 이어짐, JSON이 아닌 응답, 공고 목록(`jsonArray`) 없음, 받은 공고 수가 응답의 전체 건수(`totCnt`)보다 적음. 받은 공고 수(`fetchedCount`)는 거르기 전의 전체 공고 수다.
- 수집 범위: 지원대상(`trgetNm`)에 `소상공인` 또는 `창업벤처`가 있는 공고만 올린다.
- 빼는 공고: 신청 종료일이 판정 기준일보다 앞선 공고, 공고 식별자·이름·공식 주소·기관이 없는 공고, 같은 식별자의 두 번째 공고. 명령 출력에 사유별 개수를 남긴다.
- 지역: 공고명 앞 `[지역]` 표시나 소관기관(`jrsdInsttNm`)으로 정하지 않는다. 상품 지역은 UNKNOWN이고 지역 근거를 남기지 않으며, 지역으로 공고를 거르지도 않는다(ADR 0009 §2·§7). 대상 지역은 본문에서 AI가 읽는다. 공고명·소관기관으로 지역을 정하던 규칙은 #45·#46에서 고친 뒤에도 알려진 한계가 남아 없앴다(ADR 0009 Context).
- 상품으로 옮기는 값:
  - 상품 키는 `bizinfo-` + 공고 식별자(`pblancId`), 출처 식별자는 `BIZINFO:pblancId`다.
  - 지원 유형 `UNKNOWN`, 사업 단계 빈 배열, 용도·업종 UNKNOWN, 금리·한도·상환 조건 `null`이다.
  - 신청기간은 `YYYY-MM-DD ~ YYYY-MM-DD`만 날짜로 읽는다. 판정 기준일이 그 사이면 접수 상태가 OPEN, 아니면 UNKNOWN이다. "예산 소진시까지" 같은 문장은 날짜 없이 note에 그대로 남긴다.
  - 근거는 공고명·기관과 신청기간 표기를 `OFFICIAL_API`와 응답 checksum으로 남긴다.
  - 지원대상·지원분야 표시는 신청 전 확인 항목에 적는다. 지원분야는 `sourceCategory`에도 옮긴다(값이 없으면 남기지 않는다).
- 명령 출력: 직전 ACTIVE 릴리스에 없던 공고를 출처별로 나열한다. 운영자가 서울시 육성자금 같은 사람 관리 상품의 새 공고·변경공고를 찾는 데 쓴다.
- 공고가 기업마당에서 사라지면 다음 동기화에서 빠지고, 신청 종료일이 지나면 그 전에도 접수 종료로 판정된다.

#### 공고 본문과 AI 추출 결과 (ADR 0009)

[ADR 0009](../decisions/0009-funding-ai-condition-extraction.md)의 저장소다. funding:sync가 본문을 모아 `funding_notice_texts`에 남기고, 본문에서 AI가 읽은 조건을 `funding_condition_extractions`에 남긴다(아래 조건 추출). 남긴 조건을 사용자 입력과 맞춰 보는 규칙은 아래 맞춰 보기에 있다.

- 모으는 본문(수집기가 상품마다 만드는 본문 계획 `notice`):
  - 기업마당: API의 사업개요(`bsnsSumryCn`), 본문출력파일(`printFlpthNm`·`printFileNm`), 첨부(`flpthNm`·`fileNm`). 파일은 이름의 확장자와 파일 머리말이 모두 PDF·HWP·HWPX일 때만 텍스트로 바꾼다. 이미지·엑셀 등은 받지 않는다.
    - 한 항목의 여러 파일은 `@`로 이어 오고 주소와 이름이 같은 순서다(2026-11-03 실제 응답). 개수가 다르면 이름을 짝짓지 않아 그 파일들은 형식 아님이 된다.
    - 파일 주소의 `downloadToken`은 API 호출마다 새로 발급된다. 받을 때만 쓰고, 파일을 알아보는 주소와 `documents`에는 토큰을 뺀 주소를 쓴다.
  - 소진공: 정책자금 표의 자금 행(칸 이름을 붙인 줄)과 공통 지원자격, 연결된 접수 안내 공지의 본문 전체. 공지의 첨부(신청안내자료)는 받지 않는다.
- 합친 텍스트는 문서마다 `[문서 종류: 이름]` 줄로 시작한다. 줄바꿈을 LF로 맞추고 탭·줄바꿈 밖의 제어 문자(U+0000 포함)를 지운다.
- 문서마다 `documents`에 상태를 남긴다: 읽음, 같은 파일(바이트가 같아 한 번만 읽음), 글자 없음, 읽지 못함, 형식 아님(이름이 PDF·HWP·HWPX가 아님), 형식 다름(받은 내용이 이름의 형식과 다름. 만료된 주소의 오류 페이지 등), 너무 큼(30MB 초과), 받지 못함(404·다른 주소로 넘김 등). 이름과 오류 문장의 제어 문자도 지운다.
- 읽은 문서가 하나도 없으면 행을 만들지 않고 상품에 checksum을 적지 않는다(조건은 읽지 못함).
- 직전 ACTIVE 상품 버전의 본문과 문서 목록(파일은 주소, 출처가 준 글은 내용 checksum)이 같으면 파일을 다시 받지 않고 그 본문을 쓴다. 그 본문에 형식 다름이나 받지 못함인 문서가 있으면 다시 쓰지 않고 새로 읽는다. 같은 주소의 파일이 바뀌는 경우는 보지 못한다(기업마당 변경공고는 새 파일 식별자로 올라온다).
- 일시 장애(연결 실패, 5xx, robots.txt·403·429로 멈춤, 운영자 연락처 없음)로 파일 하나라도 받지 못하면 일부만 읽은 본문을 만들지 않고 직전 본문을 계속 쓴다. 직전 본문이 없으면 checksum을 적지 않는다. 출처 동기화는 실패로 보지 않는다.
- 상품 버전의 `noticeTextChecksum`이 바뀌면 새 상품 버전이 된다. dry run은 본문을 모으지만 DB에 쓰지 않는다.
- 기업마당 파일 받기: 처음 요청 전에 `robots.txt`를 확인해(`*`·`$` 패턴과 Allow를 RFC 9309대로 읽는다) `/cmm/fms/getImageFile.do`를 막으면 받지 않는다(2026-11-02 확인 때는 막지 않음). `www.bizinfo.go.kr`의 그 경로만 계획에 넣고 요청하며(`bizinfo.go.kr`은 같은 곳으로 읽는다), 다른 주소로 넘기는 응답은 따라가지 않고, 요청 사이 1초 이상 쉬며, User-Agent에 `FUNDING_SYNC_CONTACT`를 밝힌다. 403·429를 만나면 그 동기화에서는 더 받지 않는다. 5xx·연결 오류는 두 번까지 다시 시도한다.
- 수집한 상품의 카탈로그 규칙 검사는 파일을 받기 전에 한다. 검사에 실패할 출처를 위해 파일을 받지 않는다.
- 알려진 한계: 읽을 문서가 없는 공고와 직전 ACTIVE 릴리스에 없는 상품(사람 기록이 우선해 빠진 자동 상품 등)은 다시 쓸 본문이 없어 동기화마다 파일을 다시 받는다.
- 명령 출력에 출처별로 그대로 쓴 본문, 새로 읽은 본문, 읽을 문서 없음, 파일을 다 받지 못함의 수를 남긴다.

- `funding_notice_texts`: 상품 하나(`productKey`)의 본문과 첨부를 텍스트로 바꿔 합친 것. 소진공은 자금마다 상품이 따로라 같은 공지 본문이 자금마다 들어간다. 공고 URL, 합친 문서마다의 URL·형식·원 파일 checksum(`documents`), 처음 받은 시각을 함께 둔다. 원 파일은 저장하지 않는다.
  - `textChecksum`은 텍스트의 SHA-256이며 CHECK 제약이 강제한다. `productKey + textChecksum`이 UNIQUE라 본문이 바뀌면 새 행이 생기고, 예전과 같은 본문이 다시 오면 그 행을 다시 쓴다.
  - 상품의 지금 본문은 받은 시각이 아니라 ACTIVE 릴리스의 상품 버전이 가리키는 `textChecksum`으로 정한다. 적재에 실패한 동기화가 받은 본문은 화면에 쓰이지 않는다.
- `funding_condition_extractions`: 본문 텍스트에서 AI가 읽은 항목별 값·원문 인용(`fields`, 인용 검증 후), AI 응답 원본(`rawOutput`), 모델 id, 프롬프트 버전, 토큰 수, 추출 시각.
  - `productKey + textChecksum + model + promptVersion`이 UNIQUE라 같은 상품의 같은 본문을 같은 모델·프롬프트로 두 번 추출하지 않는다. 성공한 추출만 남긴다.
  - 결과는 `productKey + textChecksum`으로 본문 행을 가리킨다. 결과가 가리키는 본문 행은 지울 수 없고 텍스트도 바꿀 수 없다(외래키 RESTRICT와 CHECK). 그 밖의 열과 결과가 없는 본문 행은 DB가 막지 않으므로, 적재 코드가 고치거나 지우지 않는다.

#### 조건 추출 (ADR 0009 §3)

코드는 `notice-extraction.ts`다. 웹 요청 경로와 맞춰 보기(`matching.ts`·`match-list.ts`)는 이 파일과 Anthropic SDK를 import하지 않는다(테스트가 `src/app`과 맞춰 보기 파일에서 import를 따라가 확인한다). 모델·프롬프트 버전과 저장한 `fields`의 모양은 두 쪽이 함께 쓰므로 `condition-fields.ts`에 둔다.

- 언제: funding:sync가 릴리스를 적재한 뒤, 적재한 카탈로그에서 본문 checksum이 있는 상품마다 부른다. dry run은 부르지 않는다. `ANTHROPIC_API_KEY`가 없으면 부르지 않고 "키 없음"으로 센다.
- 모델 `claude-haiku-5-5`, 프롬프트 버전 `funding-conditions-v6`(v3은 음식점·카페 제외의 뜻을 밝혔고, v4는 인용 칸이 null 대신 빈 문자열을 받게 했고, v5는 프롬프트를 다시 썼고, v6은 대상 시·도가 서울 하나가 아닌 공고의 자치구를 읽지 못함으로 바꿨다). 구조화 출력(`output_config.format`)으로 항목마다 언급 여부·값·원문 인용을 받는다. 프롬프트·출력 스키마·검증 규칙 중 하나를 바꾸면 버전을 올리고, 그러면 모든 본문을 다시 추출한다. 저장한 `fields`는 저장할 때의 검증 결과다.
- 출력 스키마에서 `anyOf`·type 배열을 쓰는 칸(null 허용 포함)이 16개를 넘으면 API가 400으로 거절한다. 2026-11-04 첫 실제 동기화에서 모든 호출이 이렇게 실패했다(API가 센 수 20, 테스트의 셈 22). 그래서 인용 칸은 null 대신 빈 문자열을 받는다. 값 칸은 null을 받는다: 공고가 밝힌 조건을 스키마로 옮길 수 없을 때 쓰고, 빈 범위·빈 목록은 "제한 없음"으로 읽히므로 그 대신 쓸 수 없다. 테스트가 보내는 스키마의 칸 수를 센다(지금 14개).
- 프롬프트는 왜 읽는지(사용자 입력과 기계적으로 비교하고, 틀린 값은 사용자를 잘못 보내며, 비운 값은 확인 필요로 남는다), 신청 자격을 가리는 기준(못 맞추면 신청할 수 없는 조건만 적는다. 가점·우대와 채용할 직원의 조건은 아니다. 우대사항·가점 제목 아래 나열한 항목도 우대다), 항목의 뜻, 지어낸 공고의 예시 7건(`PROMPT_EXAMPLES`)으로 이루어진다. 예시는 테스트가 실제 검증에 통과시키고, 평가 정답의 상품 이름·인용(공백을 뺀 12자 이상)이 프롬프트에 그대로 없는지 확인한다. 평가 공고 본문은 저장소에 없어 테스트가 대조하지 못한다.
- AI에는 상품 이름과 본문을 보낸다. 공고가 여러 자금·트랙을 다루면 그 상품의 조건만 적게 한다. 일부 트랙이나 일부 신청자에게만 걸리는 조건과 트랙마다 다른 조건은 밝혔지만 형식 밖(값 null)이다.
- 구조화 출력은 선택지(enum)를 강제하지 않는다(SDK가 JSON 스키마의 enum을 설명으로 옮긴다). 선택지는 문자열로 받아 항목별로 확인하고, 선택지가 아니면 그 항목만 읽지 못함이다.
- 항목: 신청 단계(예비 창업자만·사업자만·둘 다. 제한 없음은 둘 다. 소상공인·기업·창업기업처럼 사업자를 뜻하는 말로 대상을 적으면 사업자만, 창업을 준비하는 사람은 예비 창업자, "(예비)창업자"·"(예비)창업기업"처럼 예비에 괄호를 친 말은 둘 다. "창업자"라고만 적어 알 수 없으면 형식 밖(사용자 결정 2026-11-12)), 업력과 대표자 나이(하한·상한과 상한이 미만인지. 개월은 년으로 바꾼다), 지역(전국·시·도·서울 자치구와 제외 지역. 서울 밖의 시·군·구 한정은 그 시·도로 적는다(서울 밖의 구를 서울 자치구로 적지 않는다). 본문에 구 이름만 있으면 제목의 [시·도] 표시로 시·도를 확인하되, 그 표시만으로 지역을 한정한 것으로 보지 않는다. 서울 자치구와 서울 밖이 섞이거나 서울 안에서 자치구보다 좁은 동·상권으로 한정하면 형식 밖이다. 시·도 이름은 짧은 이름(`서울`·`부산` 등)으로 맞추고, 자치구 이름은 대상 시·도가 서울 하나일 때만 서울 자치구 코드로 바꾼다), 음식점·카페 제외(제외: 음식점·카페·외식업을 제외 업종으로 밝혔거나, 신청 대상을 특정 업종·분야로 좁혔는데 음식점·카페가 없음. 식품 제조업도 음식점이 아니다. 음식점·카페가 없는 업종으로 좁혔으면 제외 업종 목록이 함께 있어도 제외다. 제외 아님: 업종 제한이 없다고 밝혔거나, 대상에 음식점·카페가 있거나, 업종을 좁히지 않고 나열한 제외 업종에 일반 음식점·카페가 없음. 유흥주점은 일반 음식점이 아니고, 목록이 "등"으로 끝나도 적힌 업종으로 판단한다), 대상 한정(청년·여성·장애인·재창업·피해 소상공인·그 밖. 매출 상한 같은 자격 조건은 그 밖. 빈 목록은 "누구나"처럼 좁히지 않는다고 밝힌 공고이고, 신청 대상을 적었을 뿐이면 언급 없음이다(사용자 결정 2026-11-12)), 신청기간(날짜 또는 원문 표기), 지원 방식(하나 이상).
- 항목 결과(`fields`)는 셋 중 하나다.
  - 읽음: 값과 인용. 업력·나이의 하한·상한이 모두 null이면, 대상 한정이 빈 목록이면 본문이 "제한 없음"이라고 밝힌 것이다.
  - 언급 없음: 본문에 그 조건이 없다. 제한 없음과 다르다(§3의 2번).
  - 읽지 못함: 언급했다면서 값이 없거나 인용이 비어 있음, 인용이 공백을 뺀 4자보다 짧음, 인용이 본문에 없음, 값이 말이 안 됨(선택지가 아님, 실제 날짜가 아님, 시작일이 종료일보다 늦음, 날짜도 표기도 없는 신청기간, 나이 0~120 밖·정수 아님, 업력 0~100년 밖, 범위에 들어갈 값이 없음(하한이 상한보다 크거나, 미만인 상한이 하한 이하), 시·도 이름이 아님, 한정한다면서 시·도·자치구가 없음, 전국인데 대상 시·도가 있음, 자치구 한정이 아닌데 대상 자치구가 있음, 대상·제외 자치구가 있는데 대상 시·도가 서울 하나가 아님(시·도가 비어 있어도 그렇다. 다른 시에도 같은 구 이름이 있어서이며, 서울에만 있는 구 이름이어도 시·도를 요구한다), 서울 자치구 이름이 아님, 지원 방식이 비어 있음).
- 인용 대조: 인용과 본문에서 가운뎃점(`ㆍ`·`·` 등)과 물결표(`～`·`~` 등)를 한 모양으로 맞추고 NFKC로 정규화한 뒤, 공백(줄바꿈·묶음 빈칸 포함)과 보이지 않는 글자(소프트 하이픈 등)를 지우고, 인용이 본문 안에 그대로 있는지 본다(사용자 결정 2026-11-03). 인용은 맞는데 해석이 틀린 경우는 막지 못한다(ADR 0009 Consequences). 인용을 항목과 묶지 않아, 다른 조건의 문장("연령 제한 없음"의 "제한 없음")을 근거로 쓴 값도 통과한다.
- 캐시: 같은 상품·본문 checksum·모델·프롬프트 버전의 결과가 있으면 부르지 않는다.
- 실패: 호출 오류, 끝까지 오지 않은 응답(`max_tokens`·거부 등, 사유를 출력에 남김), 출력 스키마와 다른 응답, 캐시·본문 조회의 DB 오류는 결과를 남기지 않고 다음 동기화에서 다시 부른다. 출처 동기화·적재 실패로 보지 않는다. 본문이 15만 자를 넘으면 보내지 않는다(잘라 보내지도 않는다). 이 상한의 토큰 수는 확인하지 않았다.
- 명령 출력에 결과별 건수와 입력·출력 토큰 합계(실패한 호출 포함), 실패 사유(앞 5건)를 남긴다. 한 번에 4건씩 부른다.

#### 조건 추출 평가

프롬프트·모델·스키마를 바꾸기 전후에 `npm --prefix app run eval:funding-conditions -- --variant <baseline|v1|…> --reps 2`로 잰다. 실제 Claude API를 부르므로 운영자가 실행한다(`ANTHROPIC_API_KEY`, `DATABASE_URL`).

- 정답: `app/eval/funding-conditions/cases.json`. 2026-11-04 동기화로 모은 공고 280건에서 어려운 유형(음식점 제외, 서울 밖 지역, 업력·나이, 여러 트랙, 소진공)을 고르게 뽑은 30건이다. 본문은 저장소에 두지 않고 앱 DB의 `funding_notice_texts`에서 (상품 키, checksum)으로 읽는다(소진공 본문 저장 확인 전). 정답은 평가 대상 모델이 아닌 Claude가 공고를 읽고 쓴 초안이고, 판단이 갈리는 칸은 `confidence: ambiguous`와 대안 정답(`alternatives`, `null`은 언급 없음도 인정)을 단다.
- 라벨링 원칙(사용자 결정 2026-11-04): 서울 밖 시·군 한정은 그 시·도로 적는다(서울 사용자에게 안 맞음). 업종 한정은 음식점·카페 제외로 적는다. 트랙마다 다른 나이·업력은 밝혔지만 형식 밖(값 null)이다. 매출 상한 같은 자격 조건은 대상 한정 OTHER이고 언급 없음도 맞음으로 본다. 가점·우대는 제한이 아니다. 신청 대상을 밝혔는데 특정 집단 한정이 없으면 한정 없음(빈 목록)도 맞음이다(2026-11-05). 트랙마다 다른 지역과, 사용자 입력에 없는 자격(벤처 인증 등)으로 넘을 수 있는 업력은 값으로 옮기지 않아도 맞음이다(2026-11-12).
- 채점(`condition-eval.ts`): 정답도 `verifyConditionOutput`을 거쳐 저장 모양으로 맞추고, 통과하지 못하는 정답이 있으면 실행하지 않는다. 값의 모양이 아니라 맞춰 보기 판정으로 비교한다. 맞춰 보기에 쓰는 여섯 항목은 판정이 갈릴 수 있는 사용자 입력마다 `matchConditions`의 판정이 모두 같으면 같은 답이다(서울 사용자에게 같은 결과인 차이는 틀림이 아니다). 입력은 비교하는 값들의 경계에서 만든다: 업력 경계 ±2개월의 개업 연월, 나이 경계 ±1세, 서울 25개 자치구, 대상 조합 8가지(리뷰 지적 2026-11-05: 정해 둔 입력은 7년·39세 같은 흔한 기준선 사이를 못 봤다). 나이 입력은 0~120세만 본다. 보여 주기만 하는 신청기간은 종료일, 지원 방식은 종류만 본다. 항목마다 맞음 / 같은 확인 필요(판정은 같고 상태만 다름) / 위험한 오답(어떤 입력에서 정답과 다른 맞음·안 맞음을 냄) / 놓침(정답과 다르지만 확인 필요로만 달라짐, 안전함) / 보여 주기 틀림으로 나눈다. 지표는 항목 정확도, 위험한 오답(여섯 항목 중), 놓침, 완전 일치다.
- 알려진 한계: 판정은 기준일 하루(2026-11-04)로 비교한다. 그래서 매달 1일·말일에만 갈리는 차이(7년 이하와 7년 미만 등)는 같은 답으로 본다. 신청기간을 못 읽었는데 정답의 종료일이 이미 지났으면 화면에서는 확인 필요 사유(AI가 읽은 종료일 지남)가 빠지지만 놓침(안전)으로 센다. 지금 정답 30건에는 해당하는 공고가 없다.
- 결과는 `.claude/hillclimb/funding-conditions/<variant>/`(저장소에 넣지 않음)에 공고·회차마다 쓰고, 이미 쓴 회차는 건너뛴다. 각 결과에 프롬프트 지문(추출 코드가 만드는 요청 전체의 해시: 모델·시스템 프롬프트·메시지 틀·출력 스키마·매개변수)을 남겨, 한 variant에 다른 프롬프트의 결과가 섞이면 실행하지 않는다. 요약은 저장한 AI 원답을 지금 검증 규칙과 정답으로 다시 채점하고(`results.jsonl`의 점수는 실행 당시 값), 계획한 공고·회차 중 점수 없는 회차(실패, `errors.jsonl`) 수와 채점하지 않은 결과(지금 공고에 없음, trace 없음)를 함께 보인다.
- 측정 기록(프롬프트 v5, 2026-11-12, 공고 30건 × 2회): 기준선 v4보다 항목 정확도 87.5→96.7%, 위험한 오답 4.4→1.4%, 놓침 8.8→1.3%다. 프롬프트를 이 30건을 보며 고쳤으므로 표본 안 결과다. 남은 위험한 오답은 업력에 몰려 있다. 우대사항 목록의 업력이 신청서 표에 다시 나오는 공고에서 그 업력을 자격으로 읽고, "○○ 스타트업 또는 창작자"처럼 한쪽 신청자에게만 걸리는 업력을 모두의 상한으로 읽는다. 둘 다 그 업력을 넘은 사업자에게 공고가 안 맞음으로 접힌다. 정답에 예비 창업자만·여성·장애인·재창업 한정·서울 자치구 한정·지역 제외 공고가 없어 이 부분의 규칙은 재지 못했다.

#### 맞춰 보기 (ADR 0009 §4)

코드는 `matching.ts`(판정)와 `match-list.ts`(읽기)다. 판정 기준일은 호출자가 넘긴다. API와 화면은 아래 맞춰 보기 API에 있다.

AI가 읽은 값으로는 공고를 숨기지 않는다. AI 값은 항목마다 맞음·안 맞음·확인 필요만 정하고(안 맞음은 접어 두되 보인다), 기본으로 숨기는 마감은 출처·운영자 데이터로만 정한다(사용자 결정 2026-11-03). AI가 읽은 값으로 공고를 숨기는 규칙을 경우마다 막다가 예외의 예외가 생기는 것을 리뷰 두 번에서 보고 정했다.

- 읽는 조건: ACTIVE 릴리스 상품 버전의 `noticeTextChecksum`으로 `funding_condition_extractions`에서 (상품 키, 그 checksum, `CONDITION_MODEL`, `CONDITION_PROMPT_VERSION`) 한 행을 읽는다. 받은 시각으로 고르지 않는다. 행이 없으면 그 공고의 항목은 모두 읽지 않음이다. 저장한 `fields`의 모양이 지금 앱과 다른 항목은 읽지 못함이다.
- 운영자 확인(ADR 0009 §3): 사람이 등록한 상품(`origin` `OPERATOR`)의 사업 단계(`eligibleBusinessStages`)와 지역(`region`)은 그 조건의 공식 원문 근거(검색 결과 요약이 아닌 evidence)가 있을 때만 AI 값 대신 쓰고, 인용 대신 근거 요약을 붙인다. 지역 SEOUL은 서울 시·도 한정, DISTRICTS는 자치구 한정이다. 미확인(빈 배열·UNKNOWN)이면 쓰지 않는다. 자동 상품의 두 필드는 쓰지 않는다. 지금 수집기는 미확인으로 두고, 그 전 릴리스에 남은 값은 수집기의 추측이다.
- 사용자 입력: 사업자등록 여부(예비 창업자·사업자), 개업 연월, 자치구, 만 나이, 대상 한정(여성·장애인·재창업. 답하지 않음과 해당 없음을 구분한다). 재난 피해 대상 공고는 범위 밖이라 피해 소상공인은 입력받지 않는다(사용자 결정 2026-11-03). 형식 검사와 자치구 보충은 호출자(`match-profile.ts`, 아래 맞춰 보기 API)가 한다.
- 항목마다 맞음·안 맞음·확인 필요다. 언급 없음·읽지 못함·읽지 않음과, 결과가 입력에 달렸는데 입력이 없는 경우는 확인 필요다. 입력이 없어도 결과가 정해지면(제한 없음을 밝힘, 제외 지역 없는 전국, 음식점·카페 제외 여부) 맞음이나 안 맞음이다.
  - 사업 단계: 둘 다면 맞음, 예비 창업자만·사업자만은 입력과 같으면 맞음.
  - 업력: 예비 창업자는 0년이다. 사업자는 개업 연월의 1일과 말일 두 끝에서 기준일까지의 기간을 상한·하한(미만·이하)과 비교해, 두 끝에서 결과가 갈리면 확인 필요다. 개월로 떨어지지 않는 연수(예: 0.3년)와 기준일보다 늦은 개업 연월도 확인 필요다.
  - 나이: 만 나이를 상한·하한(미만·이하)과 비교한다.
  - 지역: 자치구 코드로 맞춘다. 서울 제외·그 자치구 제외면 안 맞음, 시·도 한정은 서울이 있어야, 자치구 한정은 그 자치구가 있어야 맞음이다.
  - 음식점·카페: 제외면 안 맞음, 제외 아님이면 맞음.
  - 대상 한정: 그중 하나에 해당하면 맞음, 모두 해당하지 않으면 안 맞음이다. 청년은 나이 항목(청년 기준 나이)으로 맞춰 보고, 그 밖의 대상은 입력으로 알 수 없어 확인 필요다. 청년 기준 나이의 상한을 읽지 못했으면(하한만 있음) 청년인지 알 수 없다. 피해 소상공인은 해당하지 않는 것으로 본다. 그래서 피해 소상공인만 한정한 공고는 안 맞아 보임이다.
- 마감: 출처·운영자의 접수 상태가 CLOSED이거나 신청 종료일이 기준일보다 앞서면 마감이다(종료일 당일까지는 접수 중). AI가 읽은 종료일은 마감에 쓰지 않는다. 그 날짜가 지났으면 확인 필요 사유로 남긴다. 소진공은 다른 회차 공지의 날짜를 쓰지 않는데 AI는 그 공지 본문의 지난 날짜를 읽을 수 있어서다.
- 그룹: 마감 → 안 맞는 항목이 하나라도 있으면 안 맞아 보임 → 여섯 항목이 모두 맞고 접수 상태가 OPEN이며 출처가 최신이고 AI가 읽은 종료일이 지나지 않았으면 맞아 보임 → 나머지는 확인 필요(사용자 결정 2026-11-03). 출처 최신성은 자동 상품만 보고 기준은 3일이다(ADR 0006).
- 갈래(ADR 0009 §1): 자동 상품은 소진공이면 정책자금, 기업마당은 지원분야(`sourceCategory`)가 '금융'이면 정책자금이고 나머지는 지원사업이다. 사람이 등록한 상품은 대출·보증이면 정책자금, 나머지는 지원사업이다.
- 차단 목록의 자동 상품은 보여 주지 않는다(ADR 0009 §6 운영자 숨김). 출처·운영자의 결정이라 AI 값과 상관없다. 같은 공고(`sourceRef`)를 가리키는 사람 상품은 숨기지 않는다.
- 알려진 한계:
  - 항목은 서로 묶지 않는다. "청년 또는 여성"처럼 나이 상한이 일부 대상에만 걸리는 공고도 AI가 나이 값을 적으면 나이로 안 맞음이 된다(접어 둔 안 맞아 보임에 남는다, 사용자 결정 2026-11-03). 프롬프트 v5는 이런 나이를 값 없이(밝혔지만 형식 밖) 두게 한다.
  - 대상 한정은 "그중 하나"로만 읽는다. "재난 피해 청년"처럼 대상을 함께 요구하는 공고도 청년이면 맞음이 될 수 있다.
  - 나이·업력은 판정 기준일(오늘) 기준이다. 공고가 공고일 기준으로 정했으면 생일·개업 기념일 무렵에 결과가 다를 수 있다.
- 갈래마다 그룹 순서로 놓고, 같은 그룹 안에서는 릴리스 순서를 지킨다. 정책자금 카드에 쓸 공개 한도와 한도 문장(`limitText`), 사람이 등록한 상품의 운영자 지역 메모(`region.note`), 차단 목록이라 보여 주지 않은 상품 수(`hiddenCount`)를 함께 담는다.
- 활성 릴리스가 없으면 빈 결과가 아니라 `CATALOG_UNAVAILABLE`이다.

## 맞춰 보기 API

- `POST /api/funding/candidates`: 인증된 POST만 제공한다. 요청 본문의 입력으로 `listFundingMatches`(활성 릴리스와 저장한 추출 결과)를 맞춰 본다. 웹 요청은 AI를 부르지 않는다.
- 입력 스키마(`fundingMatchProfileSchema`, `match-profile.ts`): `z.strictObject`로 다음 다섯 키를 모두 받는다. 각 값의 `null`은 입력하지 않음이다. 그 밖의 키(없앤 `industryCode`·`purpose`, `asOfDate` 등)와 빠진 키는 400 `INVALID_INPUT`이다.
  - `businessStatus`: `PRE_STARTUP`(예비 창업자)·`BUSINESS`(사업자)
  - `openedYearMonth`: `YYYY-MM`, 달은 01~12이고 한국 시간 이번 달까지. 사업자일 때만 받는다(예비 창업자의 업력은 0년으로 본다)
  - `districtCode`: 서울 25개 자치구 코드
  - `age`: 0~120의 정수(만 나이). AI가 읽은 나이 조건을 받아들이는 범위와 같다
  - `targetGroups`: `WOMEN`·`DISABLED`·`RESTART` 중 한 번씩. 빈 목록은 해당 없음이고 `null`(답하지 않음)과 다르다
- 판정 기준일은 서버의 한국 시간 날짜(`todayInKst`)로 고정한다. 테스트만 `listFundingMatches`에 날짜를 주입한다.
- 상태 구분: 미로그인 401 `UNAUTHORIZED`, 잘못된 입력 400 `INVALID_INPUT`, 활성 카탈로그 릴리스 없음 503 `CATALOG_UNAVAILABLE`(빈 결과로 대신하지 않는다).
- 응답: 판정 기준일, 갈래(`tabs.POLICY_FUND`·`tabs.SUPPORT_PROGRAM`)마다 그룹별 개수와 상품(`ProductMatch`: 그룹, 항목별 읽은 값·인용 또는 운영자 근거·판정·확인 필요 이유, 보류 이유, 접수 상태·신청기간·AI가 읽은 신청기간·마감 근거, 지원 방식, 한도, 자동 상품의 출처와 마지막 성공 확인일), 사람이 등록한 상품의 기록일(`operatorRecord`)과 운영자 지역 메모, 운영자가 숨긴 상품 수(`hiddenCount`), 릴리스 정보(카탈로그 키·버전·스키마 버전·기준일·활성화 시각·상품 수), 맞춰 본 입력(`profile`).

### 계획에 저장한 조건으로 맞춰 보기

- `POST /api/plans/{id}/funding-matches`: 인증된 POST만 제공한다. 요청 본문을 받지 않고 계획에 저장된 조건으로만 맞춰 보며, 판정 기준일은 서버의 한국 시간 오늘이다. 맞춰 보기는 페이지 단위와 같은 `listFundingMatches`다.
- 계획 조건 저장: `plans.fundingProfileJson`(nullable JSON)에 위 입력 스키마의 값을 저장한다.
  - `POST /api/plans`와 `PUT /api/plans/{id}`에서 선택 항목이다. 보내지 않으면 저장된 조건을 유지하고 `null`이면 비운다. 새로 쓰는 값은 지금 모양이어야 한다(예전 모양은 400).
  - 재무 계산 입력(`inputJson`)·`INPUT_SCHEMA_VERSION`·`calculationKey`·저장된 결과 스냅샷은 바꾸지 않는다.
  - 계획 화면은 다섯 항목을 하나도 입력하지 않으면 `null`을 보낸다. 그래서 조건 없이 저장한 계획의 조회는 400이고, 사용자가 저장된 조건을 비울 수 있다.
- 예전 모양 읽기(`readStoredFundingProfile`): 5c 전의 조건(`businessStage`·`districtCode`·`industryCode`·`purpose`)은 읽을 때 사업 단계(`PRE_REGISTRATION` → 예비 창업자, `POST_REGISTRATION` → 사업자, `UNKNOWN` → 입력하지 않음)와 서울 자치구만 옮기고 업종·용도는 버린다(사용자 결정 2026-11-03). 예전 입력에 없던 항목은 입력하지 않음이다. 읽기는 저장된 값을 바꾸지 않고, 다음 계획 저장 때 지금 모양으로 쓴다. 어느 모양에도 맞지 않으면 다른 값으로 해석하지 않고 400이다. 저장된 개업 연월은 이번 달 검사를 다시 하지 않는다(저장할 때 검사했다).
- 자치구: 저장된 조건의 자치구가 비어 있으면 서버가 계획의 사업 프로필(`businessProfileJson.districtCode`)로 채워 맞춰 본다(ADR 0009 §4). 사업 프로필의 자치구만 있고 자금 조건이 없는 계획은 맞춰 보지 않는다(400).
- 상태 구분: 미로그인 401 `UNAUTHORIZED`, 없거나 타인 소유인 계획 404 `NOT_FOUND`(소유자 불일치를 403으로 구분하지 않는다), 저장된 조건이 없거나 모양이 다르면 400 `INVALID_INPUT`, 활성 카탈로그 릴리스가 없으면 503 `CATALOG_UNAVAILABLE`.
- 응답은 페이지 단위 응답에 어느 계획·revision의 조건이었는지(`plan.id`, `plan.revision`)와 자치구를 어디서 가져왔는지(`districtSource`: 자금 조건·사업 프로필·없음)를 더한다. `profile`은 자치구를 채운 뒤의 입력이다. 맞춰 본 결과는 조회 결과이며 저장하지 않는다.

### 화면

`/funding`(입력을 저장하지 않음)과 계획 화면(저장된 조건으로 조회)이 같은 입력란과 결과 표시를 쓴다.

- 입력란: 사업자등록 여부(사업자면 개업 연월), 사업장·거주 자치구, 대표자 나이, 대상 한정(여성·장애인·재창업·해당 없음 체크. 아무것도 고르지 않으면 답하지 않음). 나이·개업 연월은 입력한 글자를 앞뒤 공백만 지우고 검사해 형식이 틀리면 무엇이 틀렸는지 알리고 저장하지 않는다(계획 저장은 재무 입력과 한 요청이라, 서버의 400으로 재무 입력까지 이유 없이 저장되지 않는 일을 막는다). 브라우저의 숫자·연월 입력란은 틀린 글자를 빈 값으로 넘겨 입력하지 않음으로 바꾸므로 쓰지 않는다. 개업 연월은 iOS 숫자 키패드에 "-"가 없어 붙여 쓴 6자리(202403)와 점·빗금·공백으로 나눈 표기도 받아 `YYYY-MM`으로 바꿔 보낸다. 자치구 보충의 저장 전 변경 비교는 서버처럼 서울 자치구 코드만 본다. 장애 여부는 맞춰 보기에만 쓰고 AI에 보내지 않는다고 함께 적는다. 계획 화면은 자치구를 비우고 다른 조건을 저장하면 저장된 사업 조건의 자치구를 쓴다고 알리고, 예전 모양에서 옮긴 조건이면 그렇다고 알린다(옮길 값이 없는 예전 조건은 다음 저장 때 비워진다). 자금 조건의 자치구가 비어 있는데 사업 조건의 자치구를 바꾸고 저장하지 않았으면, 자금 조건을 바꾼 것처럼 저장 전에는 조회를 막는다.
- 결과: 맞춰 본 기준(카탈로그·기준일·판정 기준일·공고 수와 운영자가 숨긴 수·조건을 읽은 모델과 프롬프트 버전·맞춰 본 입력 요약)을 먼저 보여 주고, 정책자금·지원사업 탭으로 나눈다. 탭마다 그룹별 개수, 맞아 보임, 확인 필요, 안 맞아 보임(접어 둠), 마감(기본으로 숨기고 버튼으로 연다) 순서다. 맞아 보이는 공고가 0건이어도 정상 결과라고 알린다.
- 카드: 항목마다 판정(맞음·안 맞음·확인 필요), 읽은 값, 원문 인용(운영자 확인 값은 근거 요약, 지역에는 운영자 지역 메모), 확인 필요 이유를 문장으로 보여 준다. 보류 이유(접수 상태 미확인, 출처 확인 끊김, AI가 읽은 종료일 지남)와 마감 근거도 문장으로 쓴다. 자동 상품은 출처와 마지막 확인일을, 사람이 등록한 상품은 기록일을 보여 준다(사람 상품은 출처 최신성을 따지지 않으므로 언제 기록한 내용인지 알린다. 그룹에는 쓰지 않는다). "AI가 공고문에서 읽은 내용입니다. 신청 전 원 공고를 확인하세요"와 원 공고 링크를 붙이고, 신청 자격이나 결정이 확정된 것처럼 쓰지 않는다(`match-text.test.ts`가 화면 파일의 문구를 검사한다).
- 정책자금 탭: 카드마다 한도 문장(출처의 `limitText`, 없으면 공개 한도)과 "한도는 최대치이며 실제 금액은 심사로 정해진다"를 보여 준다. 계획 화면에서는 그 옆에 보고 있는 저장 결과의 계획 부족자금(`plannedFundingGap`)을 그 결과의 revision과 함께 참고로 보여 준다. 다시 계산하지 않으며, 저장 결과를 보고 있지 않으면 금액을 쓰지 않는다.
- 빈 상태와 오류: 활성 카탈로그 없음(503)은 0건과 다른 안내, 저장된 조건 없음·읽지 못함은 다시 입력해 저장하라는 안내, 그 밖의 오류는 오류 상자로 보여 준다.

## 저장된 대출 가정

상품 확정 조건을 계획의 신규 대출 가정으로 옮기던 기능(`POST /api/plans/{planId}/loan-assumption`과 계획 화면의 적용 버튼)은 [ADR 0009](../decisions/0009-funding-ai-condition-extraction.md) §5로 없앴다. 사용자는 대출 조건을 재무 계획에 직접 입력한다.

- 그 전에 저장된 `plans.loanAssumptionJson`(상품 키·버전·상품명·카탈로그 키·카탈로그 버전·적용 시각과 그때의 신규 대출 입력)은 그대로 읽고, 계획 화면에 어느 상품 조건인지와 승인 확정이 아님을 함께 보여 준다. 새로 쓰지 않는다.
- 계획 저장(PUT): 새 `newLoan` 입력이 저장된 출처의 값과 같으면 출처를 유지하고, 다르면 지운다. 상품 조건이 아닌 값을 상품 조건으로 표시하지 않기 위해서다. 출처를 새로 만들지는 않는다.
- 계산: 계획에 남은 출처를 `plan_results.loanAssumptionJson`으로 복사해, 그 결과에 어떤 상품 조건이 반영됐는지 남긴다. 과거 결과는 다시 계산하지 않는다.
- `loanAssumptionJson`을 다루는 API 라우트 파일은 계획 수정과 계산뿐이다(`loan-assumption.test.ts`가 `src/app/api`의 라우트 파일 이름 사용을 검사한다. 두 라우트가 출처를 새로 만들지 않는 것은 같은 파일의 라우트 테스트가 확인한다).
