# 자금 카탈로그·후보 도메인

이 문서는 카탈로그 검증·적재, 판정, API 정책을 다룬다. 카탈로그 편집 절차, 필드 기록 규칙, 현재 검수 범위는 [app/catalog/funding/README.md](../../app/catalog/funding/README.md)에 있다.

## 코드 위치

- `app/src/features/funding`: 판정 함수는 React·DB·외부 API에 의존하지 않는다.
  - 카탈로그 Zod 스키마(`schema.ts`), 규칙 검사(`validation.ts`), 고정 조건 판정(`eligibility.ts`)
  - 릴리스·상품 버전 적재, 활성 카탈로그 읽기(`read.ts`), 요청 스키마·응답 조립(`candidates.ts`)
  - 출처별 수집 결과를 사람이 관리하는 카탈로그와 합쳐 적재하는 동기화(`sync.ts`), 출처별 수집기(`sources/`)
  - 페이지 단위 후보 화면(`FundingMatcher.tsx`), 두 화면이 함께 쓰는 결과 표시(`FundingCandidatesPanel.tsx`)
- `app/catalog/funding`: 운영자가 공식 공고를 정리한 JSON 카탈로그와 갱신 절차 문서.

## 카탈로그

- 실행: `npm --prefix app run funding:validate`, `npm --prefix app run funding:load [-- --catalog <경로>]`. 기본 카탈로그는 `app/catalog/funding/catalog.json`이다.
- 원문 확인과 카탈로그 편집은 운영자가 수행한다.
- Zod 스키마가 productKey·version 형식, 필수 필드, 날짜 형식, 금액의 원 단위 정수 문자열, supportType·사업단계·접수 상태·상환방식 열거, 공식 기관 HTTPS 호스트, checksum 형식을 검사한다.
- 상환 계산은 구조화된 확정 조건 필드(`interestRatePercent`·`repaymentTermMonths`·`repaymentGraceMonths`)만 읽는다. 조건 문장(`interestCondition`·`repaymentCondition`)은 숫자로 해석하지 않는다. 기록 규칙은 카탈로그 README의 "확정 조건과 상환 계산"에 있다.
- 규칙 검사 항목:
  - productKey+version 중복
  - 접수기간과 관측 접수 상태의 모순(종료된 공고를 OPEN으로 기록 등)
  - 지원 유형과 금리·상환 조건의 모순, 확정 조건의 내부 모순
  - 원문 미확보 상태의 checksum
  - 검수 기한 경과
  - 상환 계산 사유 누락·불필요, 조건별 공식 근거 누락
- 다음은 오류가 아니라 주의로 기록한다: 검수 기한 경과, 검수자 미지정(UNASSIGNED), 공식 원문이 아닌 요약 근거, 신청기간 종료일 전의 CLOSED 기록(조기 마감이면 근거를 추가한다).
- 검수 기능이 생기기 전까지 `funding:load`는 검수자가 UNASSIGNED여도 적재한다. 그런 상품은 판정에서 현재 후보가 되지 않고 추가 확인으로 분류된다.
- 검증을 우회하는 명령행 옵션은 없다. 조건이 불명확한 상품을 강제로 활성화하는 경로를 만들지 않는다.
- 스키마 `funding-catalog-v1.1.0`은 v1.0.0에 다음을 더했다. v1.0.0으로 적재된 릴리스도 읽으며, 그때 자동화 설정은 모두 꺼진 기본값이다.
  - 상품의 `sourceRef`(출처와 공고 식별자). funding:sync가 모은 상품에 붙고, 사람이 기록한 상품도 같은 공고를 가리키면 적는다.
  - 카탈로그의 `automation`: 정책자금 자동 승격(`policyLoanPromotion`)·상환 계산 자동 승격(`repaymentPromotion`) 스위치, 차단 목록(`blockedSources`), 출처별 동기화 결과(`sourceSyncs`). 스위치는 기본으로 꺼져 있다.
- 스키마 `funding-catalog-v1.2.0`은 v1.1.0에 원문이 알려 주지 않는 값을 추측 없이 기록하는 방법을 더했다. 이전 버전의 릴리스도 읽는다.
  - 지원 유형 `UNKNOWN`(DB enum `FundingSupportType`에도 있다). 상환방식은 `UNKNOWN`이어야 하고 확정 금리·상환기간·거치를 기록할 수 없다. 금융 조건 근거를 요구하지 않는다.
  - `eligibleBusinessStages`의 빈 배열은 사업 단계 미확인이다. 이때 사업 단계 근거를 요구하지 않는다.
- 자동 상품은 검수자에 사람 대신 자동 규칙 버전(`AUTO:funding-auto-v1`)을 적는다. 규칙 검사는 다음을 오류로 본다: 출처 식별자 없는 자동 검수자, 같은 공고를 가리키는 상품 두 개, 같은 출처의 동기화 결과 두 개. 자동 상품에는 다음 검토일이 없어도 된다.
- 웹 페이지 근거(`OFFICIAL_WEB_PAGE`)의 checksum은 사람이 기록한 상품에서는 오류다(내려받은 파일이 없다). 자동 상품에서는 funding:sync가 실제로 받은 응답이므로 그 페이지의 checksum을 남길 수 있다.

### 릴리스와 상품 버전

- 릴리스에는 출처 목록(`sourceDocuments`), 이 카탈로그가 담은 상품 버전 목록(`productVersions`), 기준일(`basisDate`), 상품 검수일 중 가장 늦은 날짜(`reviewedAt`), `schemaVersion`, 카탈로그 checksum, 검증 요약을 함께 보존한다.
- 카탈로그 checksum은 파일 바이트의 SHA-256이다. `funding_catalog_releases.catalogChecksum`이 UNIQUE라서 같은 내용을 다시 적재해도 릴리스가 늘지 않고 `ALREADY_ACTIVE`로 끝난다. 같은 catalogKey+catalogVersion에 다른 내용이 오면 거부한다.
- 상품 버전(`funding_product_versions`)은 `productKey + version`이 UNIQUE이며 불변이다.
  - 이미 적재된 버전과 내용이 다르면 `PRODUCT_VERSION_IMMUTABLE`로 실패하고 기존 행을 덮어쓰지 않는다. 새 내용은 version을 올려 추가한다.
  - 릴리스와 상품 버전은 `funding_catalog_products` 연결 테이블로 묶어, 같은 불변 버전을 여러 릴리스가 재사용할 수 있다.
- 적재는 PENDING으로 시작해 적재 후 검증까지 통과한 뒤 한 트랜잭션으로 ACTIVE가 된다. 활성화는 상태 전환만 하며 과거 릴리스와 상품 버전을 지우지 않는다.
- 실패하면 이번 적재가 만든 상품 버전만 삭제하고, 이전에 이미 저장된 상품 버전은 그대로 둔다. 릴리스는 `FAILED`와 실패 사유(`오류 코드 + 메시지`)로 남는다.
- 릴리스의 `automation`(JSONB)에 자동화 설정과 출처별 동기화 결과를 저장한다. v1.0.0 릴리스는 NULL이다.

### 동기화

[ADR 0006](../decisions/0006-funding-discovery-automation.md)의 동기화다. 실행 명령은 [DEVELOPMENT.md](../DEVELOPMENT.md#로컬-데이터-준비)에 있다.

- 흐름: 출처별 수집기(`FundingSourceAdapter`)로 공고를 받아 상품을 만들고, 사람이 관리하는 `catalog.json`의 상품과 합친 뒤, 위 적재기와 같은 검사로 `PENDING → ACTIVE` 적재한다.
- 합친 카탈로그:
  - catalogKey와 검수자·스위치·차단 목록은 `catalog.json`을 따른다. 기준일은 동기화한 날(한국 시간)이다.
  - catalogVersion은 `동기화한 날.번호`다. 같은 날 적재된 릴리스와 `catalog.json`의 버전을 피해 번호를 올린다.
  - 적재한 카탈로그 파일은 `data/funding-sync/`(Git 제외)에 남는다.
- 상품 버전: 날짜와 근거 checksum을 뺀 내용이 이미 적재된 버전과 같으면 그 버전을 재사용한다. 다르면 가장 높은 버전의 PATCH를 올린다.
- 출처가 실패하면 그 출처의 상품은 직전 ACTIVE 릴리스의 것을 그대로 두고, 마지막 성공일(`lastSucceededOn`)과 공고 수도 그대로 둔다. 다음은 실패다.
  - 수집기 오류(장애·인증 오류·차단 등)
  - 빈 응답. "공고 없음"으로 해석하지 않는다
  - 받은 공고 수가 직전 성공의 절반 미만
  - 수집한 상품이 카탈로그 규칙 검사를 통과하지 못함, 다른 출처의 상품, 같은 공고 두 번, 사람이 기록한 상품 키와 겹침
- 사람이 기록한 상품이 같은 공고(`sourceRef`)를 가리키면 자동 상품을 빼고 사람 기록을 쓴다.
- `catalog.json`에 자동 검수자 상품이 있으면 거부한다. 자동 상품은 funding:sync만 만든다.
- 수집 출처와 허용 확인 기록. 출처는 robots.txt와 약관을 확인한 뒤에만 수집기를 등록한다(ADR 0006 3절).

#### 소진공 정책자금 수집

정책자금 갈래의 자동 수집 출처다(ADR 0006 1·3절). 접수 상태를 홈 화면 접수 표시로 정하고 상품을 자금 단위로 식별하는 것은 [ADR 0007](../decisions/0007-semas-ols-status-and-fund-identity.md)이 정한다. 첨부(PDF)는 읽지 않고, AI로 본문을 해석하지 않는다. 뽑은 값과 주소만 상품에 남기고 페이지 원문은 저장하지 않는다.

- 읽는 곳(모두 로그인 없는 공개 페이지):
  - 정책자금 한눈에 보기(`/ols/man/SMAN018M/page.do`): 직접대출·대리대출 표의 자금명·신청요건·대출기간·대출한도·대출금리, 공통 지원자격, 분기 기준금리.
  - 홈 화면(`/ols/man/SMAN010M/page.do`)의 "정책자금 신청하기": 자금별 접수 상태 표시("접수중")와 접수기간. ADR 0006 4절 1번의 "출처의 접수 상태 표시"로 쓴다.
  - 공지사항 목록 JSON(`/ols/man/SMAN051M/search.do`, POST): 자금별 최신 접수 안내 공지를 찾는 데만 쓴다. 조건 값은 읽지 않는다. 최근 30쪽까지 읽는다.
  - 공지 상세(`/ols/man/SMAN052M/page.do?bltwtrSeq=…&bbsTypeCd=…`): 접수기간·신청대상 문장과 '제외'가 들어간 줄.
- 요청 규칙:
  - 수집 전에 `/robots.txt`를 요청한다. 확인 때처럼 404가 아니면(새로 생기면) 멈춘다. 사람이 허용 여부를 확인해 위 표에 기록한 뒤 수집기를 고친다.
  - 요청 사이 1초 이상 쉰다(기본 1.5초). User-Agent는 `TrendBench-funding-sync/1.0 (+FUNDING_SYNC_CONTACT)`다. 연락처가 없으면 요청하지 않고 실패한다.
  - 403·429·자동 입력 방지 화면을 만나면 다시 시도하지 않고 멈춘다. 서버 오류·연결 오류만 두 번까지 다시 시도한다.
- 실패(필수 항목 없음): 자금 표·표 머리글·직접/대리 구분·공통 지원자격의 소상공인 문장·"정책자금 신청하기" 영역을 찾지 못함, 공지 목록이 JSON이 아니거나 비었거나 전체 건수보다 적음, 공지 상세의 제목·본문이 없거나 제목이 목록과 맞지 않음. 받은 공고 수(`fetchedCount`)는 표의 자금 행 수다.
- 상품 하나 = 표의 자금 한 행이다. 공지는 분기·월마다 새로 올라오므로 공지 번호 대신 대출구분과 자금명으로 식별한다.
  - 출처 식별자는 `SEMAS_OLS:대출구분:자금명`(공백과 앞머리 '소상공인'을 뺀 이름, 예: `대리대출:일반경영안정자금`)이다. 차단 목록과 사람 기록 우선도 이 식별자로 맞춘다.
  - 상품 키는 `semas-ols-direct-…`·`semas-ols-agency-…`와 식별자 SHA-256 앞 10자리다.
  - 같은 자금이 표에 두 번 나오면 뒤 행을 빼고 센다. 표에 없는 홈 화면 대출 카드는 명령 출력에 나열한다.
- 공지 고르기: 같은 대출구분의 '대출정보' 공지 중 제목에서 자금명 바로 뒤에 (직접대출)·(대리대출)·(일반)과 '접수 안내'·'신청안내'만 오는 공지 가운데 번호가 가장 큰 것. '금리인하제도 신청안내'처럼 다른 제도의 안내와 '(홈플러스 피해 소상공인)'처럼 대상을 좁힌 세부 공고는 고르지 않는다.
- 상품으로 옮기는 값:
  - 지원 유형 LOAN, 사업 단계 사업자등록 이후(공통 지원자격이 「소상공인 보호 및 지원에 관한 법률」상 소상공인), 지역 전국(공통 지원자격에 지역 제한이 없다는 이 출처의 규칙), 용도·업종 UNKNOWN(신청 전 확인), 기관 소상공인시장진흥공단.
  - 금리는 `interestCondition`에 표의 금리와 기준금리 문장을 그대로 적고 확정 금리로 기록하지 않는다. '기준금리+가산'은 변동금리이고, '고정금리(2.0%P)'는 연 금리인지 가산폭인지 모호하다. 표에 상환방식이 없어 상환방식 UNKNOWN, 상환기간·거치 null이다. 따라서 상환 계산 대상이 아니다(ADR 0006 5절).
  - 공개 한도는 대출한도 칸이 금액 하나일 때만 원 단위로 옮긴다(예: '7천만원'). 유형·용도별 금액이 여럿이면 null이다.
  - 공식 링크는 고른 공지 상세, 없으면 정책자금 한눈에 보기다.
  - 근거는 모두 `OFFICIAL_WEB_PAGE`이며, 근거마다 그 근거를 읽은 페이지 응답(한눈에 보기·홈 화면·공지 상세)의 SHA-256을 checksum으로 남긴다(ADR 0006 2절). 공지 목록까지 포함해 읽은 페이지 전체의 checksum은 출처별 동기화 결과의 `responseChecksum`에 남는다. 날마다 바뀌는 checksum은 상품 버전 비교에서 빠지므로 버전이 늘지 않는다.
  - 신청대상 문장, 세부 유형만 접수 중인 카드, 상태 판정의 모순, 제외 신호는 신청 전 확인 항목에 적는다.
- 접수 상태:
  - OPEN: 홈 화면에 그 자금(세부 유형이 아니라 자금 이름 그대로)이 "접수중"으로 표시되고, 시작일이 판정 기준일 이전이며, 종료일이 지나지 않았고, 공지의 접수 시작일·종료일과 어긋나지 않을 때만이다. 날짜 없는 '상시접수'도 "접수중" 표시가 있으면 OPEN이다.
  - CLOSED: 홈 화면 표시가 '마감'·'종료'일 때.
  - 그 밖은 UNKNOWN이다: 홈 화면에 표시가 없음, 세부 유형 카드만 있음, 알 수 없는 표시, 날짜 모순. 신청기간은 공지 접수기간으로 남기므로, 종료일이 지난 공지는 판정에서 접수 종료가 된다.
  - 홈 화면 종료일이 없고(자금소진시까지) 공지에 종료일이 있으면 공지 종료일을 쓴다.
- 제외 신호: 공통 제외업종 또는 공지의 '제외' 줄에 음식점·외식·카페 등이 보이면 OPEN으로 기록하지 않고 확인 항목에 남긴다(ADR 0006 4절 3번·6절). 유흥주점 같은 표현은 신호로 보지 않는다.
- 판정: 사업자등록 이후 대상이라 예비 창업자에게는 사업자등록 이후 검토 그룹에 나온다. 정책자금 자동 승격 스위치가 켜지고 출처가 최신이며 OPEN일 때만 현재 후보가 된다.

#### 기업마당 공고 탐색

기업마당은 새 공고를 찾는 데만 쓴다(ADR 0006 1·2절). 여기서 만든 상품은 사업 단계·지원 유형을 알 수 없어 사람이 확인하기 전에는 추가 확인에 머문다.

- 요청: `BIZINFO_API_KEY`로 하루 한 번, 요청 한 번(`searchCnt` 5000)에 현재 공고 전체를 JSON으로 받는다. 오류 문장과 명령 출력에서 키를 가린다.
- 실패: 키 없음, 403·429(다시 시도하지 않고 멈춘다), 서버 오류·연결 오류가 세 번 이어짐, JSON이 아닌 응답, 공고 목록(`jsonArray`) 없음, 받은 공고 수가 응답의 전체 건수(`totCnt`)보다 적음. 받은 공고 수(`fetchedCount`)는 거르기 전의 전체 공고 수다.
- 수집 범위: 지원대상(`trgetNm`)에 `소상공인` 또는 `창업벤처`가 있는 공고만 올린다.
- 빼는 공고: 서울 밖 공고, 신청 종료일이 판정 기준일보다 앞선 공고, 공고 식별자·이름·공식 주소·기관이 없는 공고, 같은 식별자의 두 번째 공고. 명령 출력에 사유별 개수를 남긴다.
- 지역: 공고명 앞 `[지역]` 표시가 있으면 그것으로, 없으면 소관기관(`jrsdInsttNm`) 이름으로 정한다.
  - `서울특별시 ○○구`처럼 서울 자치구가 확인되면 DISTRICTS, 서울이면 SEOUL, 다른 시·도면 뺀다.
  - 어느 것도 아니면 전국으로 추측하지 않고 UNKNOWN이다.
- 상품으로 옮기는 값:
  - 상품 키는 `bizinfo-` + 공고 식별자(`pblancId`), 출처 식별자는 `BIZINFO:pblancId`다.
  - 지원 유형 `UNKNOWN`, 사업 단계 빈 배열, 용도·업종 UNKNOWN, 금리·한도·상환 조건 `null`이다.
  - 신청기간은 `YYYY-MM-DD ~ YYYY-MM-DD`만 날짜로 읽는다. 판정 기준일이 그 사이면 접수 상태가 OPEN, 아니면 UNKNOWN이다. "예산 소진시까지" 같은 문장은 날짜 없이 note에 그대로 남긴다.
  - 근거는 공고명·기관, 신청기간 표기, 지역 표시(서울·자치구일 때)를 `OFFICIAL_API`와 응답 checksum으로 남긴다.
  - 지원대상·지원분야 표시는 신청 전 확인 항목에 적는다.
- 명령 출력: 직전 ACTIVE 릴리스에 없던 공고를 출처별로 나열한다. 운영자가 서울시 육성자금 같은 사람 관리 상품의 새 공고·변경공고를 찾는 데 쓴다.
- 공고가 기업마당에서 사라지면 다음 동기화에서 빠지고, 신청 종료일이 지나면 그 전에도 접수 종료로 판정된다.

### 판정

- 판정 규칙(`eligibility.ts`): 조건별로 PASS/FAIL/UNKNOWN을 계산한다. FAIL이 하나라도 있으면 FAIL, FAIL 없이 UNKNOWN이 있으면 UNKNOWN, 모두 PASS면 PASS다.
- REGION·PURPOSE·INDUSTRY를 포함한 각 조건에 직접 확인한 공식 근거가 없으면 UNKNOWN이다.
- 조건별 UNKNOWN의 효과([ADR 0006](../decisions/0006-funding-discovery-automation.md)):
  - 사업 단계·지역이 UNKNOWN이면 현재 후보로 확정하지 않고 추가 확인으로 분류한다. 상품의 사업 단계가 빈 배열(원문 미확인)이면 사업 단계는 UNKNOWN이다.
  - 업종·용도가 UNKNOWN이면 현재 후보를 막지 않는다. 대신 "업종: …", "용도: …" 형태로 신청 전 추가 확인(`manualChecks`)에 더한다. 이때 자격 판정(`eligibilityVerdict`)은 그대로 UNKNOWN이다.
  - FAIL은 조건과 상관없이 조건 미충족이다.
- 접수 상태 OPEN/CLOSED/UNKNOWN은 자격 판정과 별도로 유지한다.
- 신청 종료일이 판정 기준일보다 앞서면 관측 접수 상태가 OPEN·UNKNOWN이어도 접수 종료(CLOSED)로 판정한다. 종료일 당일까지는 접수 중으로 보고, 종료일이 없으면(예: 예산 소진 시까지) 관측 접수 상태를 따른다.
- 검수 기한이 지난 상품, 검수일 또는 검수자가 없는 상품, 검색 결과 요약으로만 확인한 상품은 현재 후보로 확정하지 않는다.
- 사업자등록 이후에만 검토할 수 있는 상품은 POST_REGISTRATION 상태로 현재 예비 창업자 후보와 분리한다.
- 자동 상품(검수자 `AUTO:…`)의 추가 규칙(ADR 0006). 사람이 기록한 상품은 `sourceRef`가 있어도 지금 규칙만 따른다.
  - 다음 검토일 대신 출처의 마지막 성공 동기화일로 최신성을 본다. 그날에서 3일이 지났거나 성공 기록이 없으면 검수 기한 경과(`REVIEW_OVERDUE`)다.
  - 차단 목록의 공고, 새 공고를 찾는 데만 쓰는 출처(기업마당)의 자동 상품, 지원사업(지원금·공간·프로그램)과 유형 미확인 자동 상품, 정책자금 자동 승격이 꺼진 상태의 자동 상품은 현재 후보가 아니라 추가 확인이며 사유를 표시한다.
  - 상환 계산 자동 승격이 꺼져 있으면 자동 상품은 확정 조건이 있어도 상환 계산 대상이 아니다.
- 지원 유형 표시: GRANT 지원금, GUARANTEE 보증, LOAN 대출, SPACE 공간·보육, PROGRAM 프로그램, UNKNOWN 유형 미확인(원 공고 확인).
- 갈래(`branch`, ADR 0006 1절): 저장하지 않고 지원 유형에서 정한다. LOAN·GUARANTEE는 정책자금(`POLICY_FUND`), GRANT·SPACE·PROGRAM은 지원사업(`SUPPORT_PROGRAM`)이다. UNKNOWN은 어느 쪽으로도 추측하지 않고 유형 미확인(`UNCLASSIFIED`)으로 둔다.
- 지원금·보증·공간·프로그램 지원과 유형 미확인 공고는 대출 원금이나 상환 일정으로 변환하지 않는다.
- 대출의 상환 계산 대상 여부:
  - 공개 한도, 확정 금리(`interestRateConfirmed`와 `interestRatePercent`), 상환기간·거치(`repaymentTermMonths`·`repaymentGraceMonths`), 상환방식이 모두 확정되고, 계산 엔진이 지원하는 방식이며, 거치개월이 전체 상환개월보다 작아야 상환 계산 대상이다.
  - 하나라도 어긋나면 상환 계산 대상으로 표시하지 않고 사유를 남긴다.
  - 상환 계산 대상일 때만 상품 조건을 계획의 대출 가정으로 옮길 수 있다.

## 후보 조회 API

- `/api/funding/candidates`: 인증된 POST만 제공한다. 활성 릴리스와 `funding_catalog_products`의 position 순서로 불변 상품 버전을 읽고 `evaluateCandidates`로 판정한다.
- 요청 본문은 `z.strictObject`로 다음 네 키만 받는다. 그 밖의 키는 400 `INVALID_INPUT`이다.
  - `businessStage`(PRE_REGISTRATION·POST_REGISTRATION·UNKNOWN)
  - `districtCode`(5자리 또는 null)
  - `industryCode`(CS100001 형식 또는 null)
  - `purpose`(기존 Purpose 또는 UNKNOWN)
- 판정 기준일은 서버의 한국 시간 날짜(`todayInKst`)로 고정한다. 클라이언트가 `asOfDate`를 보내면 400이며, 테스트만 `listFundingCandidates`에 날짜를 주입한다.
- 상태 구분: 미로그인 401 `UNAUTHORIZED`, 잘못된 프로필 400 `INVALID_INPUT`, 활성 카탈로그 릴리스 없음 503 `CATALOG_UNAVAILABLE`. 활성 릴리스가 없을 때 빈 후보가 아니라 503으로 알린다.
- 응답에 담는 것:
  - 카탈로그 버전·기준일·판정 기준일·검수자·스키마 버전·활성화 시각, 입력 프로필, 상태별 개수
  - 갈래별 상태 개수(`summaryByBranch`). 모든 갈래를 더하면 전체 개수(`summary`)다
  - 상품명·기관·지원 유형·갈래·후보 상태, 포함·제외·추가 확인 이유
  - 자동 상품의 출처·출처 이름·마지막 성공 확인일(`automation`). 사람이 기록한 상품은 `null`이다
  - 조건별 PASS/FAIL/UNKNOWN과 근거 id, 공식 링크·접수·검수 상태
  - 상환 계산 가능 여부와 불가 사유
- 결과 화면(`FundingCandidatesPanel.tsx`, `/funding`과 계획 화면 공통):
  - 갈래 요약(갈래별 검토 후보 수·전체 수)을 먼저 보여 주고, 정책자금·지원사업 순으로 갈래마다 상태별 개수와 상품을 나눠 보여 준다. 유형 미확인은 그런 상품이 있을 때만 마지막에 보여 준다.
  - 갈래 안에서는 상품이 있는 상태만 목록으로 보여 준다. 갈래에 상품이 없으면 그렇다고 표시한다.
  - 자동 상품 카드에는 "자동 확인" 표시, 출처, 마지막 확인일, 원 공고 링크를 함께 보여 준다(ADR 0006 7절). 검수 상태 대신 출처 확인이 최신인지 끊겼는지를 보여 준다.

### 계획에 저장한 조건으로 판정

- `POST /api/plans/{id}/funding-matches`: 인증된 POST만 제공한다. 요청 본문을 받지 않고 계획에 저장된 조건으로만 판정하며, 판정 기준일은 서버의 한국 시간 오늘(`todayInKst`)로 고정한다. 판정 로직은 새로 만들지 않고 `listFundingCandidates`를 그대로 호출한다.
- 계획 조건 저장: `plans.fundingProfileJson`(nullable JSON)에 사업단계·자치구·업종·용도를 저장한다.
  - 검증은 후보 조회 API의 `fundingCandidateRequestSchema`를 그대로 재사용한다.
  - 재무 계산 입력(`inputJson`)·`INPUT_SCHEMA_VERSION`·`calculationKey`·저장된 결과 스냅샷은 바꾸지 않는다.
  - `POST /api/plans`와 `PUT /api/plans/{id}`에서 선택 항목이다. 보내지 않으면 저장된 조건을 유지하고 `null`이면 비운다. 조건이 없는 기존 계획은 그대로 유효하다.
  - 계획 화면은 네 조건을 하나도 입력하지 않으면 UNKNOWN 프로필 대신 `null`을 보낸다. 그래서 조건 없이 저장한 계획의 후보 조회는 400이고, 사용자가 저장된 조건을 비울 수 있다.
- 상태 구분: 미로그인 401 `UNAUTHORIZED`, 없거나 타인 소유인 계획 404 `NOT_FOUND`(소유자 불일치를 403으로 구분하지 않는다), 저장된 조건이 없거나 스키마와 다르면 400 `INVALID_INPUT`, 활성 카탈로그 릴리스가 없으면 503 `CATALOG_UNAVAILABLE`.
- 판정 응답은 후보 조회 응답에 어느 계획·revision의 조건이었는지(`plan.id`, `plan.revision`)를 더한다. 자금 후보는 조회 결과이며 불변 저장 대상이 아니다.

## 상품 확정 조건 → 대출 가정 적용

- 상품 확정 조건을 계획의 신규 대출 가정으로 옮기는 일은 사용자가 계획 화면에서 명시적으로 실행할 때만 일어난다. 후보 조회·판정·계획 불러오기·초안 저장 시점에는 신규 대출 입력을 자동으로 채우지 않는다. 화면은 상품 확정 조건과 사용자가 입력한 가정을 구분해 표시한다.
- 적용 대상은 서버가 저장된 계획 조건과 활성 릴리스의 자동화 설정으로 다시 판정한 `CURRENT_CANDIDATE`이면서, 그 판정의 상환 계산 가능(`repayment.supported`)이 true인 대출 상품뿐이다. 그 밖의 상품은 "상환 계산 대상 아님 + 사유"를 유지하며 0원 상환으로 대체하지 않는다.
- 실행: `POST /api/plans/{planId}/loan-assumption`(본문 `{ productKey, version, revision }`).
  - 서버가 활성 카탈로그에서 상품 버전과 현재 후보 여부를 다시 확인한다.
  - 사용자가 초안에 저장한 `newLoan.principal`에 상품의 확정 금리·기간·거치·상환방식만 결합한다.
  - 저장된 원금이 1원 이상이고 공개 한도 이하인지 확인한다. 공개 한도는 이 검증에만 쓰며 신청·승인 원금으로 자동 대입하지 않는다.
  - 계산은 재무 계산 엔진(`app/src/features/finance`)을 그대로 쓰며 새 계산기나 별도 상환표를 만들지 않는다.
- 적용은 계획 입력의 변경이므로 기존 revision·불변 결과 규칙을 따른다. 성공하면 revision이 1 증가하고, 적용 전에 계산해 둔 과거 `plan_results`는 바뀌지 않는다.
- 출처 보존: 적용 시 `plans.loanAssumptionJson`에 상품 키·버전·상품명·카탈로그 키·카탈로그 버전·적용 시각과 실제 신규 대출 입력을 저장한다. 계산 시 그 값을 `plan_results.loanAssumptionJson`으로 복사해, 그 뒤 카탈로그가 바뀌어도 어떤 상품 조건이 반영된 결과인지 추적할 수 있다.
- 출처 삭제: 계획 저장(PUT)에서 새 `newLoan` 입력이 저장된 상품 확정 조건과 값까지 같으면 출처를 유지하고, 사용자가 값을 직접 바꾸면 출처를 지운다. 상품 조건이 아닌 값을 상품 조건으로 표시하지 않기 위해서다.
- 상태 구분: 미로그인 401 `UNAUTHORIZED`, 없거나 타인 소유인 계획 404 `NOT_FOUND`, 잘못된 본문·활성 카탈로그에 없는 상품 버전·상환 계산 대상이 아닌 상품 400 `INVALID_INPUT`, 활성 카탈로그 없음 503 `CATALOG_UNAVAILABLE`, 오래된 revision 409 `REVISION_CONFLICT`.
- 화면 규칙: 계획이 저장되어 있고 자금 조건·재무 입력에 저장하지 않은 변경이 없을 때만 적용할 수 있다. 적용 뒤에는 어떤 상품 버전·카탈로그의 조건인지와 승인 확정이 아님을 함께 표시한다.
