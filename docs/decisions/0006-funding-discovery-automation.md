# ADR 0006: 자금 후보의 승격·강등을 공식 API로 자동화

- Status: Proposed
- Date: 2026-09-25
- Owners: 미정 (자동 규칙과 차단 목록 책임자. Accepted 전에 지정)
- Related issue/PR: #5, #13, #15
- Supersedes: 없음

## Context

자금 후보 기능은 동작하지만 보여 줄 후보가 없다. 2026-09-25 기준 카탈로그 `2026-09-23.1`의 상태는 다음과 같다.

- **현재 후보 0건:** 상품 5개 모두 검수자가 `UNASSIGNED`라서, 어떤 계획에서도 현재 후보가 되지 않는다(AGENTS.md §3의 8번).
- **상환 계산 가능 0건:** 대출 3개 모두 금리가 확정되지 않아 계획의 대출 가정으로 적용할 수 없다.
- **곧 기한 경과:** 서울시 중소기업육성자금 3개의 재검수일이 2026-10-20이다. 강북창업지원센터는 이미 기한이 지났고, 예비창업패키지는 접수가 끝났다.
- **병목은 사람의 시간:** 운영자가 기관 사이트를 돌며 공고를 찾고, JSON에 옮겨 적고, 기한마다 다시 확인한다. 이 방식으로는 5개도 기한 안에 유지하지 못하고 있다.

공고를 구조화된 형태로 주는 공식 Open API가 두 개 있고, 2026-09-25에 두 API 모두 활용신청했다. 아래 항목은 공개된 이용 사례에서 확인한 것이며, 실제 응답은 구현 전에 다시 확인한다.

- **K-Startup 공고 정보**(창업진흥원, `apis.data.go.kr/B552735/kisedKstartupService01`, `getAnnouncementInformation01`)
  - 주는 값: 공고명, 접수 시작·종료일, 지원 지역, 신청 대상, 창업 업력, 지원 분야, 모집 진행 여부, 상세 페이지 URL. 하루 한 번 갱신된다.
  - 키: 공공데이터포털 인증키(지금 `SEMAS_SERVICE_KEY`)를 쓴다.
  - 한계: 지역 조건을 서버가 적용하지 않고 다른 지역 공고가 섞여 오는 사례가 보고됐다. 요청 조건 대신 응답 항목의 지역 값으로 거른다.
- **기업마당 지원사업정보**(중소벤처기업부, `www.bizinfo.go.kr/uss/rss/bizinfoApi.do`)
  - 주는 값: 공고 ID, 공고명, 소관·수행기관, 신청기간(`YYYYMMDD ~ YYYYMMDD` 문자열), 지원대상(자유 서술), 사업개요, 공고 URL, 분야·지역 해시태그. 중앙부처와 지자체 공고를 함께 모은다.
  - 키: 기업마당에서 발급하는 별도 인증키가 필요하다.

두 API 모두 업종 제한·자금 용도·금리·한도·상환기간·거치를 구조화된 값으로 주지 않는다. 이 조건은 공고문 본문과 첨부(PDF·HWP)에만 있다.

지금 판정 규칙(`eligibility.ts`)으로는 자동화된 상품이 현재 후보가 될 수 없다. 막는 곳은 네 군데다.

1. **검수자:** 사람 검수자가 있어야 현재 후보가 된다.
2. **업종·용도:** 둘 중 하나라도 `UNKNOWN`이면 추가 확인으로 분류된다. 그런데 API에는 두 값이 없다.
3. **대출·보증:** 금융 조건의 1차 근거가 있어야 현재 후보가 된다.
4. **ACTIVE 릴리스:** ACTIVE 릴리스는 하나뿐이다(`read.ts`). 따라서 자동으로 모은 상품과 사람이 기록한 상품을 한 릴리스로 합쳐야 한다.

현재 판정에는 빈틈도 하나 있다. `evaluateProduct`는 신청기간을 보지 않는다. 그래서 OPEN으로 기록한 상품은 신청 종료일이 지나도 재검수일까지 현재 후보로 남는다. 지금은 OPEN 상품이 없어 드러나지 않았다.

지켜야 할 제약은 다음과 같다.

- 웹 요청 중에는 외부 데이터를 가져오지 않는다(AGENTS.md §2).
- 적재는 `PENDING → ACTIVE` 검증을 거치고(§3의 9번), provenance를 보존한다(§3의 10번).
- 자료 부족이나 장애를 빈 성공으로 위장하지 않는다(§3의 2번).
- 사용자에게 승인처럼 말하지 않는다(PRODUCT.md 원칙 5).

## Decision

기본 원칙은 세 가지다.

- 공식 API의 구조화 값으로 확인되는 조건은 자동으로 판정하고, 그 결과에 따라 현재 후보로 올리고 내리는 일을 사람 없이 한다.
- 구조화 값이 없는 조건은 추측하지 않고 "신청 전 확인"으로 표시한다.
- 확인이 끊기면 자동으로 내린다.

### 1. 동기화 명령: `funding:sync`

운영자 명령 하나가 다음을 차례로 한다.

1. K-Startup과 기업마당에서 공고를 받는다.
2. 자동 규칙으로 카탈로그 상품을 만든다.
3. 사람이 관리하는 `app/catalog/funding/catalog.json`의 상품과 합친다.
4. `funding:validate`와 같은 검사를 거쳐 새 릴리스로 적재한다(`PENDING → ACTIVE`).

세부 규칙은 다음과 같다.

- **실행 주기:** 하루 한 번 실행한다(K-Startup의 갱신 주기).
- **실행 위치:** 정기 실행 위치(배포 플랫폼 cron, GitHub Actions 예약 실행 등)는 #15에서 배포 환경과 함께 정한다. 그 전까지는 운영자가 직접 실행한다.
- **상품 식별과 재사용:** 자동 상품은 출처와 공고 ID로 식별한다. 내용이 같으면 기존 불변 상품 버전을 재사용하므로 상품 버전이 날마다 늘지 않는다.
- **같은 공고가 두 번 있을 때:** 사람이 기록한 상품이 같은 출처 공고를 가리키면 사람 기록이 우선한다.
- **근거와 검수자 기록:**
  - 자동 상품의 근거는 `retrievalMethod: OFFICIAL_API`이고, 출처 API·공고 ID·조회 시각·응답 checksum을 남긴다.
  - `reviewer`에는 사람 이름 대신 자동 규칙 버전(예: `AUTO:funding-auto-v1`)을 적는다. 규칙을 바꾸면 버전을 올린다.

### 2. 자동 승격 조건

자동 상품은 다음을 모두 만족할 때만 현재 후보가 된다.

1. **지원 유형:** 구조화된 지원 분야에서 지원금·공간·프로그램(`GRANT`·`SPACE`·`PROGRAM`)으로 정해진다. 대출·보증은 자동 승격하지 않는다(4절).
2. **신청기간:** 시작일과 종료일이 모두 날짜로 확인되고, 판정 기준일이 그 사이에 있으며, 출처의 모집 진행 표시와 모순이 없다. "상시", "예산 소진 시까지" 같은 문구는 날짜가 아니므로 승격하지 않는다.
3. **사업 단계와 지역:** 구조화 값으로 PASS다. 지역은 서울 또는 전국만 해당한다. 자치구 한정 공고는 API로 구분할 수 없으므로, 서울 공고는 지금처럼 "서울 대상, 자치구 추가 확인"으로 표시한다.
4. **제외 신호 없음:** 지원대상·사업개요 자유 서술에 제외 신호가 없다. 예를 들어 음식점·외식·유흥 제외, 제조·기술 등 특정 업종 한정 같은 키워드다. 키워드는 내리는 데만 쓰고, 올리는 근거로는 쓰지 않는다.
5. **차단 목록:** 사람이 관리하는 차단 목록에 없다.
6. **최신성:** 마지막으로 성공한 동기화가 판정 기준일로부터 3일 이내다.

### 3. 업종·용도 규칙 변경

- 업종·용도가 `UNKNOWN`이어도 현재 후보를 막지 않는다. 대신 "신청 전 확인: 업종 제한과 자금 용도는 공고문에서 확인하세요"를 후보에 붙인다.
- 이 규칙은 자동 상품과 사람이 기록한 상품에 똑같이 적용한다.
- `FAIL`(명시된 제외)은 지금처럼 막는다. 사업 단계·지역·신청기간이 `UNKNOWN`이면 지금처럼 막는다.

### 4. 대출·보증과 상환 계산

- 대출·보증은 금리·한도가 판단의 핵심인데, 구조화 출처에 없다. 그래서 자동 승격하지 않고 추가 확인으로 둔다.
- 사람이 금융 조건 근거를 기록하면 기존 규칙대로 현재 후보가 되고, 조건이 확정되면 상환 계산도 할 수 있다.
- "상환 계산 가능"으로의 자동 승격은 이 ADR의 범위가 아니다.

### 5. 자동 강등

다음은 사람 없이 적용한다.

- **신청 종료:** 신청 종료일이 판정 기준일보다 앞서면, 관측 상태가 OPEN이어도 CLOSED로 판정한다. 사람이 기록한 상품에도 적용한다.
- **출처 변경:** 출처가 모집 종료를 표시하면 CLOSED로 바꾼다. 공고가 사라지거나 내용이 바뀌면 다음 동기화에서 다시 판정한다.
- **제외 신호:** 제외 신호가 새로 보이면 추가 확인으로 내린다.
- **최신성 초과:** 동기화가 3일 넘게 성공하지 않으면 자동 상품은 현재 후보에서 빠진다. 파이프라인이 멈추면 후보가 저절로 내려가는 안전장치다.

### 6. 실패 처리

- **새 릴리스를 만들지 않는 경우:** 출처 하나라도 장애·인증 오류이거나, 빈 응답이거나, 받은 공고 수가 직전 성공 대비 절반 미만으로 줄면 새 릴리스를 만들지 않는다. 이때 기존 ACTIVE를 유지한다(§3의 9번).
- **"공고 없음"으로 해석하지 않는다:** 실패를 "공고 없음"으로 해석해 상품을 지우지 않는다.
- **실패가 이어질 때:** 최신성 규칙(5절)에 따라 자동 상품은 3일 뒤 현재 후보에서 빠진다.

### 7. 사람의 역할과 표시

- **사람이 하는 일:**
  - 자동 규칙과 차단 목록을 관리한다. 차단 목록에는 출처·공고 ID·사유를 적고 `catalog.json`에 둔다.
  - 대출·보증의 금융 조건을 기록한다.
  - 오판 신고를 처리한다.
- **사람이 기록한 상품:** 지금처럼 `nextReviewAt` 규칙을 따른다.
- **자동 승격 끄기:** 스위치를 하나 둔다. 끄면 자동 상품은 추가 확인으로만 표시되고, 강등은 계속 동작한다.
- **화면 표시:** 자동 상품에는 "자동 확인" 표시, 마지막 확인 시각, 출처 API, 원 공고 링크, 신청 전 확인 항목을 함께 보여 준다. 후보는 검토 시작점이지 선정·승인이 아니라는 안내를 유지한다.

### 8. 범위 밖

- 공고문 본문·첨부를 AI로 해석해 조건을 확정하는 일. `docs/PRODUCT.md`의 "자동 공고 해석" 제외는 "공고문 본문의 자동 해석"으로 좁혀서 유지한다.
- 기관 웹사이트 스크래핑.
- 웹 요청 중의 외부 조회, 공고 원문 파일의 저장소 보관.

### 9. Accepted 뒤 함께 고칠 문서

- AGENTS.md §3의 8번: "미검수"를 "사람 검수 또는 ADR 0006의 자동 확인을 거치지 않은"으로 고친다. 업종·용도 `UNKNOWN`의 처리를 이 ADR에 연결한다.
- `docs/PRODUCT.md`: 자금 후보 행과 제외 범위를 고친다.
- `docs/domains/funding.md`: 동기화·승격·강등 규칙을 적는다.
- `docs/DEVELOPMENT.md`: 기업마당 키 `BIZINFO_API_KEY`와 `funding:sync`를 적는다.

## Alternatives considered

- **사람 검수만 유지(#5의 선택지 1):** 규칙은 바뀌지 않는다. 하지만 병목이 사람의 시간이라 상품 수를 늘릴 수 없다.
- **자동 탐색 + 사람 승인으로 승격(이 ADR의 첫 초안):** 사람의 일은 줄지만, 병목이 그대로 남는다. 검수 책임자가 없으면 현재 후보가 계속 0건이다.
- **검수 관리 화면 구현(#5의 선택지 3):** 관리자 역할이라는 새 권한 모델이 필요하다. 사람 검수를 전제로 하므로 병목이 남는다.
- **업종·용도 `UNKNOWN`은 계속 막기:** 두 API에 업종·용도가 없으므로 자동 승격이 되어도 현재 후보는 0건이다. 결과적으로 선택지 1과 같다.
- **AI로 공고문을 해석해 업종·용도·금리를 채움:** 한 번 잘못 읽으면 틀린 자격 판정이나 틀린 상환액이 된다(§3의 1·8번, PRODUCT.md 원칙 7). 필요해지면 별도 ADR로 다룬다.
- **출시에서 숨기거나 베타로 표시(#5의 선택지 4):** 이 ADR은 기능을 줄이기보다 운영을 자동화하는 쪽을 제안한다.

## Consequences

- **장점:**
  - 사람 없이 현재 후보가 생긴다.
  - 마감·변경·삭제가 날마다 반영된다.
  - 파이프라인이 멈추면 후보가 저절로 내려간다.
- **비용·위험:**
  - **자동 오판:** 첨부 공고문에만 음식점 제외가 적혀 있으면, 그 공고가 현재 후보로 보일 수 있다. 다음 네 가지로 줄인다.
    - 업종 "신청 전 확인" 표시
    - 제외 신호 강등
    - 차단 목록
    - 표본 점검과 자동 승격 스위치(Validation)
  - **현재 후보의 의미 변화:** 업종·용도를 확인하지 않은 상품도 현재 후보가 된다. 화면이 이 차이를 분명히 보여 주어야 한다.
  - **외부 API 의존:** 외부 API 두 개에 의존하고, 인증키가 하나(기업마당) 늘어난다.
- **migration·호환성:**
  - 카탈로그 상품에 출처 공고 식별자를 추가하고, 카탈로그에 차단 목록을 추가하고, `schemaVersion`을 올린다.
  - 릴리스·상품 버전 테이블은 그대로 쓴다. 최신성은 릴리스 기준일로 판단하므로 새 테이블이 필요 없다.
  - 릴리스는 하루 하나씩 늘어난다(연 약 365개).
- **운영·보안·데이터 영향:**
  - 키는 `app/.env.local`과 운영 비밀값에만 둔다.
  - 웹 요청은 DB만 읽는다.
  - 판정 규칙이 바뀌므로, 같은 상품이라도 규칙 변경 전후의 후보 상태가 다를 수 있다.
  - 자금 후보는 저장하지 않는 조회 결과라, 과거 계산 결과는 바뀌지 않는다.

## Validation

- **단위 테스트:**
  - 신청 종료일이 지나면 OPEN 상품도 CLOSED다.
  - 업종·용도 `UNKNOWN`은 현재 후보를 막지 않고 신청 전 확인으로 표시된다. `FAIL`은 막는다.
  - 자동 승격 조건 여섯 개를 각각 하나씩 어기면 현재 후보가 되지 않는다.
  - 대출·보증 자동 상품은 현재 후보가 되지 않는다.
  - 동기화가 3일을 넘기면 자동 상품은 현재 후보에서 빠진다.
- **동기화 테스트:**
  - 출처 장애·빈 응답·급감 때 새 릴리스가 만들어지지 않고 기존 ACTIVE가 유지된다.
  - 같은 공고의 사람 기록이 자동 상품보다 우선한다.
  - 차단 목록의 공고는 현재 후보가 되지 않는다.
- **첫 실행 기록:** 첫 실제 실행 뒤 받은 공고 수, 자동 상품 수, 현재 후보 수를 이 ADR에 기록한다.
- **표본 점검:** 첫 4주 동안 매주 자동 현재 후보를 최대 10건씩 사람이 원문과 대조해 오판(실제로는 서울 예비 음식점·카페 창업자가 신청할 수 없는 공고)을 기록한다.
- **중단 조건:** 어느 한 주라도 오판이 표본의 20%를 넘으면 자동 승격 스위치를 끈다. 규칙을 고쳐 다시 점검할 때까지 강등만 유지한다.
