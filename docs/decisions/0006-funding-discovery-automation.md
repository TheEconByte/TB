# ADR 0006: 자금 공고 탐색과 재확인을 자동화하고 승격만 사람이 승인

- Status: Proposed
- Date: 2026-09-25
- Owners: 미정 (Accepted 전에 검수 책임자와 함께 지정)
- Related issue/PR: #5, #13, #15
- Supersedes: 없음

## Context

자금 후보 기능은 동작하지만 보여 줄 후보가 없다. 2026-09-25 기준 카탈로그 `2026-09-23.1`의 상태는 다음과 같다.

- **현재 후보 0건:** 상품 5개 모두 검수자가 `UNASSIGNED`라서, 어떤 계획에서도 현재 후보가 되지 않는다(AGENTS.md §3의 8번).
- **상환 계산 가능 0건:** 대출 3개 모두 금리가 확정되지 않아(`interestRateConfirmed=false`) 계획의 대출 가정으로 적용할 수 없다.
- **곧 기한 경과:** 서울시 중소기업육성자금 3개의 재검수일이 2026-10-20이다. 강북창업지원센터는 이미 기한이 지났고, 예비창업패키지는 접수가 끝났다.
- **병목은 사람의 시간:** 운영자가 기관 사이트를 돌며 공고를 찾고, 필드를 JSON에 옮겨 적고, 기한마다 다시 확인한다. 검수 경고(검수자 미지정·기한 경과·1차 원문 아님)는 이미 `funding:validate`에 있다. 없는 것은 이 일을 계속할 사람이다.

공고를 구조화된 형태로 주는 공식 Open API가 두 개 있다. 아래 항목은 공개된 이용 사례에서 확인한 것이며, 실제 응답은 구현 전에 다시 확인한다.

- **K-Startup 공고 정보**(창업진흥원, `apis.data.go.kr/B552735/kisedKstartupService01`, `getAnnouncementInformation01`)
  - 주는 값: 공고명, 접수 시작·종료일, 지원 지역, 신청 대상, 창업 업력, 모집 진행 여부, 상세 페이지 URL. 하루 한 번 갱신된다.
  - 키: 공공데이터포털 인증키(지금 `SEMAS_SERVICE_KEY`)를 쓰며, 이 API에 대한 활용신청이 따로 필요하다.
  - 한계: 지역 조건을 서버가 적용하지 않고 다른 지역 공고가 섞여 오는 사례가 보고됐다.
- **기업마당 지원사업정보**(중소벤처기업부, `www.bizinfo.go.kr/uss/rss/bizinfoApi.do`)
  - 주는 값: 공고 ID, 공고명, 소관·수행기관, 신청기간(`YYYYMMDD ~ YYYYMMDD` 문자열), 지원대상(자유 서술), 사업개요, 공고 URL, 분야·지역 해시태그. 중앙부처와 지자체 공고를 함께 모은다.
  - 키: 기업마당에서 발급하는 별도 인증키가 필요하다.

두 API 모두 금리·한도·상환기간·거치·업종 제한·자금 용도를 구조화된 값으로 주지 않는다. 이 조건은 공고문 본문과 첨부(PDF·HWP)에만 있다.

현재 판정에는 빈틈이 하나 있다. `evaluateProduct`는 신청기간을 보지 않는다. 그래서 검수를 마치고 OPEN으로 기록한 상품은 신청 종료일이 지나도 재검수일까지 현재 후보로 남는다. 지금은 OPEN 상품이 없어 드러나지 않았다.

지켜야 할 제약은 다음과 같다.

- 웹 요청 중에는 외부 데이터를 가져오지 않는다(AGENTS.md §2).
- 미검수·종료·근거 부족 상품은 현재 후보로 표시하지 않는다(§3의 8번).
- 적재는 `PENDING → ACTIVE` 검증을 거치고(§3의 9번), provenance를 보존한다(§3의 10번).
- `docs/PRODUCT.md`는 "자동 공고 해석"을 제외 범위로 둔다.

## Decision

기본 원칙: **상품을 "덜 현재적인" 상태로 바꾸는 강등은 자동으로 적용한다. 현재 후보나 상환 계산 가능 상태로 올리는 승격은 사람이 승인해야만 일어난다.**

### 1. 자동 탐색: `funding:discover`

- 운영자 명령이 K-Startup과 기업마당에서 공고를 받는다. 그중 제품 범위에 들 가능성이 있는 공고만 검수 대기 목록으로 만든다. 기준은 지역이 서울 또는 전국이고, 대상이 예비 창업자·소상공인·초기 창업기업인 공고다.
- 공고마다 구조화 필드로 채울 수 있는 값만 채운 카탈로그 상품 초안을 만든다. 형식은 기존 `fundingProductSchema`를 그대로 따른다.
  - 채우는 값: 이름, 기관, 공식 URL, 신청기간, 접수 상태. K-Startup이 구조화해 주는 경우에는 사업 단계와 지역도 채운다.
  - 근거: `retrievalMethod: OFFICIAL_API`로 기록하고, 출처 API·공고 ID·조회일·응답 checksum을 남긴다.
  - 채우지 않는 값: 금리·한도·상환·업종·용도는 `null` 또는 `UNKNOWN`으로 둔다.
  - `reviewer`는 `UNASSIGNED`로 둔다. 그래서 초안은 기존 규칙대로 현재 후보가 되지 않는다.
- 자유 서술 필드(지원대상, 사업개요)는 키워드로 분류해 검수자에게 "힌트"로만 보여 준다. 조건 판정(PASS·FAIL)의 근거로는 쓰지 않는다.
- 이미 카탈로그에 있는 상품은 출처 공고 ID로 맞춰 보고, 바뀐 필드만 보여 준다.
- 초안은 파일로 출력한다. 검수자가 초안을 `app/catalog/funding/catalog.json`에 옮기는 PR이 검수 기록이 된다. 새 DB 테이블이나 관리자 화면은 만들지 않는다.

### 2. 자동 강등: 사람 없이 적용

1. **판정 시점 날짜 규칙(순수 함수):**
   - 신청 종료일이 판정 기준일보다 앞서면, 관측 상태가 OPEN이어도 CLOSED로 판정한다.
   - 신청 시작일이 판정 기준일보다 뒤면 현재 후보가 아니다.
2. **출처 재확인: `funding:recheck`**
   - 운영자 명령이 ACTIVE 카탈로그의 상품을 출처 공고 ID로 다시 조회한다.
   - 결과는 `SAME`·`CHANGED`·`REMOVED`·`CLOSED`·`FAILED` 중 하나로, append-only 재확인 기록에 남긴다. 기록에는 상품 버전, 확인 시각, 출처, 응답 checksum을 함께 둔다.
   - 판정은 상품별 가장 최근 기록을 읽는다. `CLOSED`면 CLOSED, `CHANGED`·`REMOVED`면 추가 확인으로 강등한다.
3. **실패는 강등 근거가 아니다:**
   - API 장애·인증 오류·빈 응답은 `FAILED`로 기록하고 판정에 쓰지 않는다. 빈 응답을 "공고 없음"(`REMOVED`)으로 바꾸지 않는다(§3의 2번).
   - 재확인 기록이 없거나 전부 `FAILED`면 강등하지 않는다. 이때는 기존 검수 기한 규칙(`nextReviewAt`)이 안전망이다.

### 3. 승격: 사람 승인

- 현재 후보가 되려면 지금처럼 검수자가 지정된 카탈로그 버전이 `funding:load`로 ACTIVE가 되어야 한다. 판정 규칙(`eligibility.ts`)의 승격 조건은 바꾸지 않는다.
- 검수자가 하는 일은 두 가지다.
  - 초안에 자동으로 채운 값을 공식 원문과 대조한다.
  - 자동으로 채울 수 없는 조건(업종·용도·금리·한도·상환)을 원문에서 확인해 기록한다.
- `OFFICIAL_API` 근거는 지금처럼 1차 근거로 인정한다. 단, 구조화 필드에서 온 값에만 해당하며, 자유 서술 필드의 키워드 분류는 근거가 아니다.
- **검수 주기:**
  - 자동 재확인: 주 1회 이상.
  - 사람 재검수: 재확인이 `CHANGED`·`REMOVED`를 알릴 때마다, 그리고 적어도 90일마다(`nextReviewAt`은 `reviewedAt`에서 90일 이내).
- **검수 책임자:** 이 ADR을 Accepted로 바꾸기 전에 이름을 적는다. 비어 있으면 Accepted로 바꾸지 않는다.

### 4. 범위 밖

- 공고문 본문·첨부를 AI로 해석해 조건을 확정하는 일. `docs/PRODUCT.md`의 "자동 공고 해석" 제외는 "공고문 본문의 자동 해석"으로 좁혀서 유지한다. 초안 작성 보조로 쓰는 방안은 필요해지면 별도 ADR로 다룬다.
- 기관 웹사이트 스크래핑. Open API가 있는 두 출처부터 시작한다.
- 사람 승인 없는 승격, 웹 요청 중의 외부 조회, 공고 원문 파일의 저장소 보관.
- 정기 실행 위치(배포 플랫폼 cron, GitHub Actions 예약 실행 등)와 결과 전달 방식. #15에서 배포 환경과 함께 정한다. 그 전까지는 운영자가 두 명령을 직접 실행한다.

## Alternatives considered

- **사람 검수만 유지(#5의 선택지 1):** 규칙 변경은 없다. 하지만 병목이 사람의 시간이라 상품 수를 늘릴 수 없고, 5개도 기한 안에 유지하지 못하고 있다.
- **검수 관리 화면 구현(#5의 선택지 3):** 관리자 역할이라는 새 권한 모델이 필요하다. 지금 인증에는 역할이 없다. 카탈로그 PR이 이미 변경 내용·검수자·시점을 남기므로, 화면 없이도 검수 기록이 된다.
- **공식 API 필드만으로 사람 없이 승격:** 지원대상은 자유 서술이고, 지역 조건을 서버가 적용하지 않는 사례도 있어 잘못 판정할 위험이 있다. 게다가 업종·용도는 API에 없어서 어차피 `UNKNOWN`으로 남으므로, 현재 후보가 되지 않는다.
- **AI로 공고문을 해석해 금리·기간을 채움:** 한 번 잘못 읽으면 곧바로 틀린 상환액이 된다(§3의 1·8번). 근거 없는 정밀도를 만들지 않는다는 원칙(PRODUCT.md 원칙 7)과도 맞지 않는다.
- **출시에서 숨기거나 베타로 표시(#5의 선택지 4):** 이 ADR은 기능을 줄이기보다 운영 비용을 낮추는 쪽을 제안한다. 첫 검수가 끝나기 전에 출시하게 되면 그때 화면 처리를 #15 출시 점검에서 정한다.

## Consequences

- **장점:**
  - 검수자의 일이 "찾고 옮겨 적기"에서 "원문과 대조하고 승인하기"로 줄어든다.
  - 마감·변경·공고 삭제가 사람 없이 판정에 반영되어, 종료된 상품을 현재 후보로 보여 줄 위험이 줄어든다.
- **비용·위험:**
  - 외부 API 두 개에 의존한다. API가 멈추면 탐색이 멈추고, 재확인은 `FAILED`로 남아 기존 기한 규칙으로 돌아간다.
  - 인증키가 하나(기업마당) 늘어난다.
  - 사람 검수가 없으면 현재 후보는 여전히 0건이다. 자동화가 검수 책임자를 대신하지 않는다.
- **migration·호환성:**
  - 카탈로그 상품에 출처 공고 식별자(출처와 공고 ID) 필드를 추가하고 `schemaVersion`을 올린다. 식별자가 없는 기존 상품은 재확인 대상에서 빠진다.
  - 재확인 기록 테이블을 새 migration으로 추가한다. 기존 릴리스·상품 버전 테이블은 바꾸지 않는다.
- **운영·보안·데이터 영향:**
  - 키는 `app/.env.local`과 운영 비밀값에만 둔다.
  - 웹 요청은 DB만 읽는다.
  - 재확인 기록은 판정 근거이므로 지우지 않는다.

## Validation

- 신청 종료일이 판정 기준일보다 앞서면 OPEN 상품도 CLOSED로 판정하는 단위 테스트.
- `funding:discover` 초안이 `funding:validate`를 통과하고, `reviewer`가 `UNASSIGNED`이며, 현재 후보가 0건인지 확인하는 테스트.
- 재확인 기록 테스트:
  - 최근 기록이 `CHANGED`·`REMOVED`인 상품은 현재 후보가 되지 않는다.
  - `FAILED`만 있거나 기록이 없으면 판정이 바뀌지 않는다.
  - API 오류와 빈 응답은 `REMOVED`로 기록되지 않는다.
- 첫 실제 실행 뒤 탐색 공고 수, 검수 초안 수, 검수 후 현재 후보 수를 이 ADR에 기록한다.
- **중단 조건:** 두 번 연속 검수 주기 동안 탐색 초안 중 검수를 통과한 상품이 0건이면 출처와 필터를 다시 검토한다. 그래도 없으면 #5의 선택지 4(출시에서 숨김)로 돌아간다.
