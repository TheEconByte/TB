# TrendBench 방향 전환 분석

> 역사 자료: 이 문서는 2026-09-09 방향 전환 당시의 정적 분석 기록이며 현재 구현 지침이 아니다. 현재 기준은 [문서 지도](README.md)에서 찾는다. 분석 대상이던 이전 POS 코드는 현재 작업 트리에서 제거되었다.

분석일: 2026-09-09

이 문서는 저장소 문서와 현재 코드의 대조 결과다. 제품 결정을 새로 승인하는 문서가 아니며, 아래의 **확정된 방향**, **구현 상태**, **분석상 제안**을 구분해 읽는다.

## 1. 결론과 분석 기준

TrendBench의 중심은 **공공 상권 데이터와 개별 사업의 매출·비용을 연결해 입지·업종 안정성, 손익분기점, 상환 여력, 정책자금 후보를 제공하는 소상공인 금융 의사결정 지원 플랫폼**으로 이동했다.

기존 POS 분석 코드는 선택 입력과 상세 분석의 기반으로 재사용한다. 새 제품의 기본 흐름은 POS 없이 완료되어야 한다.

분석 시 발견한 브랜치 차이가 중요하다.

| 구분 | 확인한 상태 |
|---|---|
| 현재 작업 브랜치 | `dev`, `8c223897cd2fe8f77d844fc1e1e3179774d08c72` |
| 방향 전환 문서 | 로컬에 보관된 원격 추적 브랜치 `origin/jh-1`, `29f9579d7ab5c0f0ebb19326995dc95fe007893f` |
| 결정일 | 새 제품 컨텍스트와 Accepted ADR의 기준일은 2026-09-02 |
| 변경 범위 | 두 커밋의 차이는 문서·작업 지침·이슈/PR 템플릿 16개 파일이다. 애플리케이션과 인프라 코드는 동일하다. |
| 해석 | 방향 전환은 문서에 반영되어 있으나, 새 핵심 기능의 구현 완료를 의미하지 않는다. |

원격 fetch와 외부 API 조회는 수행하지 않았다. 따라서 위 기준은 **로컬에서 확인 가능한 저장소 이력**이며, 원격 서버의 최신 상태를 보증하지 않는다. 브랜치 전환·병합 없이 분석했다.

## 2. 무엇이 바뀌었는가

| 항목 | 기존 `dev` 문서 | 새 방향 문서 |
|---|---|---|
| 제품 목적 | 매출 하락 원인과 매장 운영 패턴 판단 보조 | 사업성·비용 감당 능력·상환 여력·자금 조달 경로 판단 보조 |
| 핵심 사용자 | 영업 중인 소상공인 점주 | 예비 창업자와 영업 중인 사업자 |
| 시작점 | POS 매출리포트 XLSX 업로드 | 사업단계·주소·업종·비용·자금 계획 입력 |
| 매출 입력 | 원본 XLSX 필수, CSV 기준 설계 금지 | 수기 → 표준 CSV → POS XLSX → Toss POS API 순으로 확장 |
| POS의 위치 | 제품의 중심이자 필수 진입 조건 | 실제 매출을 보강하고 메뉴·시간대·요일 등을 분석하는 선택 수단 |
| Give-to-Get / 익명 peer benchmark | 핵심 정체성과 보상 구조 | 새 핵심 흐름·백로그·릴리스 조건에 포함되지 않음 |
| 공공데이터 | 강남구·한식 기본값, 월별 시장 통계 | 서울 범위, 분기·상권코드·서비스업종코드 기반 상대 안정성 |
| 실제 사업 데이터 | 주문·상품·일별 매출 중심 | 월매출·할인·환불·비용·기존 부채 중심 |
| 분석 결과 | 매출·메뉴·시간대·요일 원인 진단 | 상권 안정성 + 사업 안정성 + 재무 시나리오 + 정책자금 적합도 |
| 모델 역할 | 규칙 기반 원인 진단 | 상권은 설명 가능한 기준 모델, 재무·추천은 결정적 계산과 규칙 |
| 기본 화면 | 통계 조회 → 업로드 → 내 가게 분석 | 기본정보 → 상권 → 실적·비용 → 재무 → 정책자금 |
| 개발 구조 | 공공데이터/POS 팀별 문서와 통합 계약 | 도메인 경계, 검증 가능한 기능 단위, 백로그와 ADR 중심 |

Give-to-Get을 영구 폐기했다고 명시한 별도 결정은 확인되지 않는다. 다만 이를 계속 필수 진입 조건으로 적용하면 POS 선택 입력이라는 새 결정과 충돌한다. 향후 핵심 요구로 자동 승계해서는 안 된다.

전환 이유는 ADR에 명시되어 있다. POS 사업자별 파일 차이와 업로드 부담이 크고, 기본 매출 분석의 차별성이 제한적이므로 공공 상권·개별 사업 재무·정책자금을 한 의사결정 흐름으로 연결하는 데 집중한다.

## 3. 새 제품에서 확정된 기준

### 사용자별 흐름

**예비 창업자**는 주소·업종·예상 비용·자기자금·희망 자금을 입력한다. 상권 참고값과 명시적인 매출 가정으로 손익분기점과 상환 시나리오를 확인하고 창업·정책자금 후보를 탐색한다. 존재하지 않는 실제 매출 이력을 요구해서는 안 된다.

**영업 중 사업자**는 주소·업종·최근 12개월 월매출·실제 비용·기존 부채·희망 자금을 입력한다. 실제 사업 안정성과 상권 안정성을 각각 확인하고 상환 후 잔여현금과 정책자금 후보를 받는다. 수기 월매출만으로도 전체 흐름을 완료할 수 있어야 한다.

### 서로 다른 네 가지 결과

| 결과 | 근거 데이터 | 결과의 의미 |
|---|---|---|
| 입지·업종 안정성 | 공공 상권 시계열과 경쟁점포 정보 | 같은 업종·시점의 비교집단 내 상대적 안정성 |
| 사업 안정성 | 실제 월매출·비용·주문·환불 | 매출 변동성, 비용 충당과 현금흐름 상태 |
| 재무 시뮬레이션 | 입력 비용·부채·신규 자금 조건·시나리오 가정 | 손익분기점과 악화·기본·개선 시나리오의 상환 부담 |
| 정책자금 적합도 | 검수된 상품 조건과 사업자 입력 | 추천·조건부 추천·제외 및 판정 근거 |

공공 추정매출을 개별 점포의 실제 매출로 대체하거나 두 데이터를 동일한 학습 목표로 섞지 않는다. 상권 점수는 개별 점포 생존확률이나 공식 신용점수가 아니다. 금융상품 자격과 순위는 규칙·계산으로 결정하고, LLM은 공고문 추출과 설명 보조에 한정한다.

### MVP 범위

- 지역: 서울. 상권 데이터는 문서가 지정한 서울시 상권분석서비스의 2021년 이후 공개 데이터 범위에서 확보한다.
- 경쟁점포: 소진공 상가정보를 현재 경쟁 밀도 보완에 사용한다.
- 금융상품: 소진공 및 서울 지역 정책자금·보증상품 10~20개를 공식 공고 기반으로 검수한다.
- 입력: 수기 월매출·비용이 기본이며 CSV·기존 XLSX·Toss 테스트 연동으로 확장한다.
- Toss POS: 테스트 가맹점 연결과 주문 동기화까지 포함한다.
- 제외: 실제 대출 심사·중개·신청 대행, 전국 모델, 모든 POS 지원, Toss 실가맹점 배포·웹훅, Kafka·Airflow.

Toss는 사용자에게 선택 기능이지만, 현재 백로그의 전체 MVP 릴리스 게이트에는 테스트 동기화 검증이 포함되어 있다.

## 4. 기술·데이터 설계의 변화

React·TypeScript·Vite, Java 21·Spring Boot, PostgreSQL 15, ClickHouse 24.8과 Apache POI 기반은 유지한다. 큰 변화는 기술 교체보다 도메인과 데이터 계약의 확장이다.

| 영역 | 새 책임 |
|---|---|
| `store` | 사업단계 `PLANNED/OPERATING`, 주소, 정규화된 지역·상권·업종 코드 |
| `market` | 서울 데이터 수집·검증, 분기 특징 데이터, 상대 안정성 점수 |
| `performance` | 수기·CSV·XLSX·API를 공통 월별 실적으로 정규화하고 비용·출처 저장 |
| `diagnosis` | 입력과 분석 실행, 버전이 고정된 결과 스냅샷 |
| `funding` | 상품 버전, 검수, 자격 규칙, 추천과 제외 근거 |
| `integration.tosspos` | 테스트 연결, 주문 동기화, 중복 방지와 오류 상태 |
| 기존 `upload` | POS 파일 파싱과 상세 분석을 보강하여 재사용 |

PostgreSQL은 운영 입력·상품 규칙·연동 상태·결과 스냅샷을 맡고, ClickHouse는 원천·집계 매출·공공 시계열·분석 특징을 맡는다.

공통 파이프라인은 `Raw → Staging → Normalized → Feature → Snapshot`이다. 이름 대신 코드로 결합하고, 주소의 상권 매핑과 업종 변환에 버전을 둔다. 원천 출처·기준일·수집 시점·checksum을 보존한다.

월별 실적의 공통 필드는 총매출, 할인, 환불, 순매출, 주문 수, 객단가, 입력 출처와 신뢰도다. 데이터가 부족하면 `INSUFFICIENT_DATA`와 누락 항목을 반환한다. 미확인 상품 조건은 `REVIEW_REQUIRED`로 남긴다.

분석 결과는 시장 데이터, 매장 데이터, 업종 매핑, 상품, 모델/규칙의 버전과 계산 시점을 보존해야 한다. 이후 데이터가 갱신되어도 이전 결과를 재현할 수 있어야 한다.

## 5. 문서와 현재 구현의 차이

아래는 코드·초기 SQL의 정적 확인 결과다. 테스트 실행이나 실제 DB 상태 검증 결과가 아니다.

| 영역 | 코드에서 확인한 상태 | 새 방향으로 필요한 작업 |
|---|---|---|
| 인증·사용자·매장 | 관련 controller/service/entity와 테스트 파일 존재 | 기존 기반 재사용, 신규 진단·매장 단위 소유권 검증 연결 |
| 매장 정보 | `Store`와 초기 SQL에 이름·좌표 등 존재 | 사업단계·표준 코드·주소 및 업력 입력 보강 |
| 공공 통계 | 지역명·업종명과 `business_area_name = '전체'`로 월별 통계 조회 | 코드·분기 기반 서울 데이터와 실제 안정성 점수 경로 추가 |
| POS 파싱·분석 | 세 핵심 시트 파싱, 원천 적재, 일별·메뉴·시간대·요일 분석 존재 | 선택 입력으로 연결하고 공통 월별 실적 모델에 정규화 |
| POS 소유권 | 업로드 서비스의 매장 검증은 양수 여부이며 상태 조회는 업로드 ID로 조회. 분석 서비스도 사용자 소유권 판정 없이 저장소 호출 | 사용자↔매장↔업로드 소유관계를 서버에서 검증 |
| POS 합계 대사 | 결제 합계 파싱 결과를 업로드 서비스에서 받아 저장·비교하지 않음 | 상품 상세 합계와 차이를 저장·판정하는 대사 구현 |
| 취소·중복 | 취소 행과 같은 `(orderNo, productName, optionName)`의 항목을 제외하는 방식 확인. 업로드 경로에 기간·내용 기반 중복 차단이 보이지 않음 | 부분 취소를 수량·금액으로 연결하고 재업로드·재시도 중복 방지 |
| 진단 결과 | 초기 SQL은 진단 유형·요약·업로드 참조 위주 | 입력·버전·구조화 결과를 보존하는 진단 스냅샷 모델 |
| 재무·정책자금·Toss | 소스 목록에서 해당 신규 도메인 구현을 확인하지 못함 | 새 핵심 기능 구현 필요 |
| 프론트엔드 | `App.tsx`는 백엔드 health 상태만 표시 | 로그인·대시보드·5단계 진단·관리자 화면 구축 |
| 설정 | `application.yml`과 `application.yaml` 동시 존재 | 실제 적용값을 확인한 뒤 설정 역할 통합 |

소유권 검증은 인증 여부와 별개다. 현재 Security 설정에 인증 요구가 있어도, 로그인한 사용자가 다른 매장의 ID를 지정하는 것을 막는 서비스 검증은 추가로 필요하다.

현재 백로그는 총 **35개 항목(P0 24개, P1 11개)**이며 모두 `TODO`다. 이는 문서에 기록된 상태이며, 기존 인증·POS 코드가 전혀 없다는 의미는 아니다.

## 6. 구현 전에 명확히 해야 할 사항

아래는 문서 간 차이와 분석에서 확인한 정의 공백이다. 이 보고서가 임의로 제품 기준을 확정하지는 않는다.

| 항목 | 현재 공백 또는 차이 | 정리할 내용 |
|---|---|---|
| 문서 기준 브랜치 | 현재 `dev`에는 CSV 금지·POS 필수인 구문서가 남음 | 새 방향 문서의 통합 기준을 명확히 하고 구문서의 적용 종료를 표시 |
| 새로운 API 계약 | 기존 통합 계약은 새 브랜치에서 삭제되었고 신규 API는 플레이북·화면 명세에 계획 형태로 분산 | 요청·응답·오류·소유권·상태·버전 규격을 구현 단위별로 확정 |
| 진단 수명주기 | 입력 수정·재계산 API와 불변 스냅샷 요구가 함께 존재 | 수정 가능한 초안과 고정된 계산 결과를 구분하고 재계산 결과의 새 버전 정책 정의 |
| 예비 창업자 매출 | 제품 문서는 매출 가정을 허용하나 공통 실적 스키마는 실제 실적 중심 | 계획값/실제값 구분, 가정의 출처, 실적 성장률 미산출 상태 정의 |
| 최근 12개월과 성장률 | 3·6·12개월 성장률의 비교기간이 미정 | 전기 대비·전년 동기 대비 여부와 필요 개월 수 명시. 12개월 합계의 전년 동기 비교라면 24개월이 필요 |
| 입력 출처와 품질 | `dataConfidence` 예시가 SELF_REPORTED·STANDARD_CSV 같은 입력 방식 위주 | 입력 방식과 기간 완결성·누락·대사 성공·검증 수준을 구분 |
| 폐업 압력 목표값 | 향후 4분기 집계라는 방향만 확정 | 정확한 산식·분모·비교집단·업종/경계 변경·타깃 완결 여부 정의 |
| 상권 점수 표현 | 0~100 안정성과 상대 폐업 위험을 함께 설명 | 높은 점수가 안정성을 뜻하는지, percentile 변환·라벨 경계·낮은 표본 수 처리 확정 |
| 재무 시뮬레이션 | 핵심 식은 있으나 상환방식·금리·거치·비용 분류의 상세 계약이 부족 | 비용 중복 차감 방지, 월별 상환 일정, 0금리·상환액 0·변동비율 경계·반올림 규칙 정의 |
| 추천 판정 상태 | 자격 통과 상품만 순위화하는 원칙과 `CONDITIONAL`, 화면의 `CLOSED`가 함께 존재 | 자격 상태·접수 상태·추천 상태를 구분하고 미확인 조건의 노출·정렬 방식 명시 |
| P1과 릴리스 게이트 | 프론트엔드·Toss는 P1이지만 전체 릴리스 조건에는 포함 | P1을 선택 삭제 대상으로 읽지 않도록 구현 순서와 출시 필수 여부를 별도 표시 |
| 지원 화면의 작업 누락 | 화면 명세에 회원가입·대시보드·매장관리·상품검수·데이터작업 화면까지 있으나 프론트 백로그는 5개 핵심 화면 중심 | 각 지원 화면과 API를 어떤 항목에 포함할지 또는 별도 작업으로 둘지 명시 |

특히 상권 모델은 진단 시점에 사용 가능했던 특징과 완결된 타깃으로 평가해야 한다. 최신 분기의 향후 4분기를 아직 관측하지 못했다면 이를 학습 정답으로 채워 넣을 수 없다.

## 7. 권장 실행 순서

새 백로그의 범위를 유지하면서 실제 사용자 흐름을 빠르게 검증하기 위한 **분석상 제안**이다.

1. **문서 기준과 기반 정리**: 방향 전환 문서의 적용 브랜치를 정하고 TB-001~005의 사업단계·코드, 소유권, 스냅샷, 설정, migration을 작은 작업으로 진행한다. 기존 API를 계속 노출한다면 소유권 검증을 우선한다.
2. **입력부터 재무 결과까지 연결**: TB-201~206과 TB-501·503·504를 연결한다. 운영 사업자는 수기 실적, 예비 창업자는 명시적 가정으로 비용·손익분기점·3개 시나리오를 확인하게 한다.
3. **서울 상권의 최소 데이터 경로 완성**: TB-101~107과 TB-502를 연결한다. 한 데이터셋의 수집·코드 매핑·품질 검증부터 시작해 분기 특징과 기준 모델로 확장한다.
4. **검수된 정책자금 결과 연결**: TB-301~306과 TB-505를 연결한다. 상품 버전·자격 판정을 먼저 고정하고, 검수된 10~20개 상품의 근거와 공식 링크를 제공한다.
5. **입력 확장과 운영 검증**: TB-401~406을 수행해 CSV·XLSX·Toss 테스트 입력을 같은 월별 모델에 연결한다. 기존 POS 보강은 해당 기능을 사용자에게 공개하는 시점에 맞춰 완료한다.
6. **두 사용자 유형의 종단 검증**: POS 없는 예비 창업자와 수기 실적 사업자가 입력부터 결과 저장까지 완료하는지 확인하고, 전체 릴리스 전에 Toss 중복 동기화 검증과 지원·관리자 화면 범위를 충족한다.

여기서 2번은 전체 MVP의 조기 검증 경로다. 상권 분석·정책자금·Toss 등 기존 릴리스 조건을 축소하거나 완료로 간주하는 제안이 아니다.

## 9. 근거와 검증 범위

새 결정 원문은 고정 커밋의 [제품 방향 ADR](https://github.com/TheEconByte/TrendBench/blob/29f9579d7ab5c0f0ebb19326995dc95fe007893f/docs/decisions/0001-product-direction.md), [제품 컨텍스트](https://github.com/TheEconByte/TrendBench/blob/29f9579d7ab5c0f0ebb19326995dc95fe007893f/docs/00_TrendBench_Project_Context.md), [백로그](https://github.com/TheEconByte/TrendBench/blob/29f9579d7ab5c0f0ebb19326995dc95fe007893f/docs/09_MVP_Backlog.md), [화면 명세](https://github.com/TheEconByte/TrendBench/blob/29f9579d7ab5c0f0ebb19326995dc95fe007893f/docs/10_Frontend_Screen_Spec.md)다. 이 링크의 내용은 웹 조회가 아니라 로컬 Git 객체로 읽었다.

구현 상태 대조에는 당시 저장소의 Java 백엔드, React 프런트엔드, PostgreSQL·ClickHouse 구성과 POS 업로드·분석 코드를 사용했다. 해당 파일은 현재 작업 트리에서 제거되었으며 필요한 경우 삭제 이전 Git 이력에서 확인한다.

이 작업에서는 문서와 코드의 정적 대조만 수행했다. 애플리케이션·DB·외부 API를 실행하지 않았고, 실제 상품 조건과 외부 데이터의 현재 가용성을 검증하지 않았다. 구현 코드는 수정하지 않았다.
